# 页面框架与组件库抽离评估

评估对象：把 `src/components/` 的 chrome 组件、`src/utils/ui/` 的 mixin、`tokens/theme/rail/paging` 从本工程抽成可被多个词典笔小程序共用的框架层（独立目录或独立包），页面只留业务。

平台硬约束见 [`平台约束与自检.md`](平台约束与自检.md)；当前 `utils/ui` 结构见 [`UI架构与自检.md`](UI架构与自检.md)，本文不重复那张契约表。

## 结论

1. **现在不做物理抽离。** 先把框架边界钉在本工程内（§六 S0），等触发条件出现再搬（§六 S1）。
2. **构建链不是障碍，已经实测。** 工程根目录之外的 `.vue` 能正常编译进包，代价是 `app.json` 里 4 行 alias（§四）。
3. **抽离的主要成本是接口口径，不是搬家。** 两个现有消费者（BetterPenNcm / BetterPenSys）的 chrome 语义已经分叉：主题机制、左栏状态词汇、令牌基准各自不同（§二）。合库必须先回答"以谁为准"。
4. **真正被混淆的另一半是页内重复。** 8 个列表页各写一遍分页/排序/多选接线，这部分收益在本工程内部就能拿到，不需要跨应用抽离（§五）。

## 一、框架层现在是什么

按"是否依赖本工程业务"分类，`src` 内 vue + js 共 25,418 行（页面 23 个 10,999 行 ≈ 43%，`components` 2,613 行，其余为 `utils`）。

| 层 | 文件 | 行数 | 是否可跨应用 |
|---|---|---|---|
| 外壳组件 | `PageShell` 87 / `NavRail` 174 / `PageTopbar` 103 / `ContextSheet` 177 | 541 | 可（需解掉主题依赖） |
| 小件 | `OptChip` 65 / `OptToggle` 36 / `HintToast` 64 / `EmptyHint` 34 / `CueRow` 94 | 293 | 可 |
| UI mixin | `frame` 48 / `multi` 80 / `arm` 75 / `toast` 51 / `pagebus` 55 | 309 | 可 |
| 值表与主题 | `tokens.js` 103 / `common.less` 45 / `theme.js` 235 / `rail.js` 39 / `paging.js` 39 | 461 | 半可（`theme.js` 混了品牌预设） |
| 域组件 | `SongRow` 328 / `LibraryRow` 135 / `ArtistRow` 164 / `PlaylistCard` 91 / `AlbumCard` 143 / `LyricPanel` 528 / `NowLyric` 136 / `NowProgress` 95 | 1,620 | 否 |

框架候选合计 **1,604 行**（≈ `src` 的 6%）。依赖方向当前已经是单向的：`pages → components → utils/ui | utils/theme → utils/config | assets/icons`。问题不在方向，在**同一层里混了两种命**：chrome 与域组件同在 `src/components/`，`theme.js` 里既有可复用的运行时（`bindTheme`/`accentMixin`/`pickOn`）又有本工程的品牌预设（`PRESETS`/`ACCENTS`）。

## 二、两个已有消费者已经分叉

`dev/BetterPenSys`（系统管理工具，9 页 3,719 行）复制了 chrome，之后各自演进：

| | BetterPenNcm | BetterPenSys |
|---|---|---|
| PageShell / NavRail / PageTopbar / HintToast | 87 / 174 / 103 / 64 | 71 / 200 / 90 / 54 |
| 底色与主题色 | 运行时 `theme.js` + 内联 `:style`，设置页可换 7 色 | 编译期 LESS `@bg`/`@accent`，写死青绿 |
| 左栏槽位状态 | `{on, danger, disabled}` 三个布尔 | `{nav, busy, on, off, danger}` 五语义 + spinner 帧 + `off` 变体图标 + 左侧竖条 |
| 令牌 | `tokens.js` 唯一源，生成 `common.less` 令牌段 | 手写 `common.less`，无值表 |
| 行高/主题 | `@row-h` 23vh、`@accent` 红 | `@row-h` 12vh、`@accent` 青绿 |

三条差异都是**语义**而非样式，合库必须先裁决：

1. **主题**：`PageShell` 现在自己混 `accentMixin` 取色。共享版要么改成吃 `:bg` prop（22 个页面全改调用点），要么框架自带 theme 模块、由 app 注入 `PRESETS`/`ACCENTS` 与配置读写（`theme.js:30` 目前直接 import `config.js`，那是本应用的 `ncm_settings` KV）。
2. **左栏状态词汇**：Sys 的 `busy/off` 是 Ncm 没有的。做成并集则 Ncm 的 `btnStyle`（`NavRail.vue:80`）多两条永不命中的分支；做成插件式则要先把 `btnStyle`/`iconOf` 从组件里提成可注入函数。
3. **令牌基准**：两个 `common.less` 的行高与主色已经不同，共享值表得先定"谁迁就谁"，而 Ncm 那套是被 `gen_tokens.py` 硬校验的（`scripts/gen_tokens.py:28` 固定生成到 `src/styles/common.less`）。

## 三、抽离要付的账

| 项 | 具体代价 |
|---|---|
| 双端回归 | 框架改动要在两个应用各构建 + 装机一次。本次实测构建 **2m10s**；装机还要走 `uninstall` 的数据备份/恢复（`install.sh`） |
| 自检脚本 | `scripts/theme_verify.py` 的 `CHECKS` 按 40+ 条 `src/...` 路径逐文件断言，且第 157 行只巡 `src/pages/`；框架搬家 = 两个脚本重写路径与规则 |
| LESS 解析面 | `getLessPaths` 只解析到 `<appRoot>/src/<item>`（`aiot-vue-cli/src/libs/common.js:79-80`），跨目录样式库要么走相对路径 `@import`，要么补 `lessPaths`（后者未实测） |
| 样式模块说明符 | 样式 import 用**文件名**（`falcon-vue.js:66`、`:90`）再按 importer 目录解析（`:172`）——跨目录安全，但同一目录内不能有同名 `.vue` |
| 依赖管理 | 本机 pip 无网（npm 未验证），"框架包"只能是兄弟目录 + alias：无版本号、无锁、无 CI，回滚靠人 |
| 文档 | `AGENTS.md` 的结构表、`docs/UI架构与自检.md` 的契约表、`docs/README.md` 索引都要改 |

## 四、可行性实测

**做法**：在 `dev/shared/pen-fw/spike/FwSpike.vue` 放一个带 scoped LESS 的最小组件；`src/app.json` 加 `"options": {"alias": {"@fw": "../shared/pen-fw"}}`；`pages/settings/settings.vue` import 它并挂在 `v-if="fwSpikeOn"`（`false`）上；跑 `bash scripts/build.sh`。

**结果**：构建成功，产物里能查到该组件 —— `strings .falcon_/settings.js.bin` 出现 `FwSpike`、`fws-t`、`../shared/pen-fw/spike/FwSpike.vue`。说明跨目录 `.vue` 被正常编译、scoped 类名正常生成，并**内联进消费页的 chunk**（未单独切 chunk）。

**原理依据**：alias 由 `app.json` 的 `options.alias` 提供，值按工程根解析（`aiot-vue-cli/src/libs/rollup.config.js:42-45`、`:79-80`）；`app.json` 就是构建 meta 的来源（`libs/appinfo.js:221-223`）；`.vue` 过滤器无路径限制（`rollup-plugins/falcon-vue.js:162`）。

**还原**：`src/app.json` 与 `pages/settings/settings.vue` 已 `git checkout` 还原，`dev/shared` 已删除。副作用：`build/*.amr` 被这次构建覆盖（内含一个 `v-if=false` 的死分支，行为无差异），下次构建即覆盖。

**未验证**：真机运行（本次只到构建期）；两个应用共用同一份框架时的 chunk 归属与包体积变化。

## 五、页内重复才是当下的大头

框架层抽得再干净，页面里的接线仍在各写一遍：

| 模式 | 出现页面数 |
|---|---|
| `loadMore` / `hasMore`（分片渲染） | 9 / 8 |
| `visible`/`shown` 三元组 | 4 |
| `ContextSheet` + `sortOptions` 排序浮层 | 3（dlalbums / dlartists / plinfo） |
| `multiSelectMixin` 多选 | 5 |
| `armMixin` 二次确认 | 9 |
| `toastMixin` | 12 |

典型列表页（`dlartists.vue` 215 行）里约 55 行是骨架接线：2 条组件 import + 4 条 utils import、`components` 注册、`shown/hasMore/visible`、`barSub`、`rail`、`mounted` 里 `$page.on('show')` 与 `beforeDestroy` 的 off、`loadMore`。收成一个 `listPageMixin` 能覆盖 8 个页面，合计约 300~400 行，并顺手消掉各页分页口径的漂移。这是**本工程内部**的收敛，与是否跨应用抽离无关。

## 六、建议：分两步，先钉边界再搬家

### S0（现在就做，半天，零跨应用风险）

不搬文件、不改 import。产出三样：

1. **方向规则 + 自检**：`src/components/**` 与 `src/utils/ui/**` 不得 import `utils/ncm/**`、`utils/player/**`、`utils/cover.js`、`utils/artistmeta.js`。加进 `theme_verify.py` 作一道硬校验（`ContextSheet`/`NavRail` 现在只依赖 `theme/tokens/log`，规则一加即可通过；`SongRow`/`ArtistRow` 属于域组件，列入豁免清单）。这条能抓住"框架偷偷长回业务"的漂移，比搬家更直接。
2. **契约文档**：在 `docs/UI架构与自检.md` 补一节"框架层边界与所有权"：哪些文件算框架、对外接口、改动它要回归哪些页面（chrome 改动 = 全部页面；`NavRail` 几何改动 = 所有贴栏浮窗）。
3. **`listPageMixin`**：8 个列表页共用的分页/排序面板/多选 rail 组装（§五）。

`S0` 不做的：不建 `src/fw/` 目录。`.vue` 没法用转发文件掩盖搬家（SFC 不能整体 re-export），一搬就要改 22 个页面的 import，收益归零。

### S1（触发即做，1.5–2 天）

**触发条件（任一）**：

- 第三个应用或正式化探针需要同一套页面骨架；
- BetterPenSys 再次需要同步改 chrome（说明复制已开始腐化）；
- 框架层改动频率上升到跨端回归成本可以摊销的程度。

**内容**：`dev/shared/pen-fw/` + `app.json` 的 `options.alias`（本次已实测）+ `lessPaths`（未实测，先单独冒烟）；`theme.js` 拆成 `theme-runtime`（`bindTheme`/`accentMixin`/`pickOn`/`fgIcon` 契约）+ 各 app 自己的 `PRESETS`/`ACCENTS`；Sys 只迁 chrome（`PageShell`/`NavRail`/`PageTopbar`/`HintToast` + `frame`/`toast` mixin），左栏状态词汇做成可注入的 `btnStyle`/`iconOf`，Sys 的五语义留在 Sys 侧。

### 不抽离清单

`SongRow` / `LibraryRow` / `ArtistRow` / `PlaylistCard` / `AlbumCard` / `LyricPanel` / `NowLyric` / `NowProgress` / `cover` / `artistavatar` / `quality` / `download` 系列 —— 这些编码的是网易云域知识（封面缓存、音质档位、下载归属、歌词定位），放进共享层只会把域知识搬到错误的位置。

## 七、待澄清

1. 抽离的目标是"跨应用复用"还是"防漂移"？若是后者，S0 的方向自检已经覆盖，不必搬家。
2. BetterPenSys 是否继续维护？不维护则 S1 的第一条触发条件长期不成立。
3. 共享 `PageShell` 接受哪种主题接口：吃 `:bg` prop（页面传色，最薄）还是自带 theme 模块 + app 注入预设（页面零改动，但框架持有配置读写）？
