# 应用存储：目录契约、索引库与两项格式自评估

> 本文是存储层的**唯一契约**：所有模块都按 §2 / §3 / §4 的路径与字段实现，
> 不在各自文件里另拼路径。路径的唯一真源是 [`../src/utils/paths.js`](../src/utils/paths.js)。
>
> ## ⚠️ 两条硬规矩
>
> 1. **所有文本数据进 SQLite，不写文本文件。** 平台 `fs` 没有写入接口（`writeFile`/`rename`/
>    `unlink` 都是 `undefined`），写文件只能借 shell 重定向，一次就是一次 fork（S7 真机
>    92~139ms），超过 60KB 还要分片、每片再一次 fork。134KB 的播放快照一次落盘实测 **2511ms**。
> 2. **用原生 `sqlite3` 模块，不要用 `sqlite3` CLI。** `import('sqlite3')` 在 S7 上可用
>    （`Database` + `prepare/bind/step/run/columnNameList/finalize` 全通，中文与引号逐字节无损）。
>    同样的 134KB，原生 bind+step 写入 **10ms**、读回 2ms。CLI 那条路每次调用一次 fork，
>    还得把 SQL 写临时文件再 `.read`（命令行参数会被代码页转换，中文变乱码）。
>
> 详细代价对照与通道约束见 [`存储层.md`](存储层.md)。
>
> ```
> data/
>     local_index.db（索引表 + kv 文档表 + 曲目元数据/歌词）
>     downloads/<track_id>/{track.mp3|flac, cover.jpg}
>     cache/<track_id>/{track.mp3|flac, cover.jpg}
> ```

## 0. 两项自评估的结论（先给答案）

### 0.1 封面：**不需要多个尺寸**，`covers/` → `cover.jpg`

现状是 `covers/<key>_<size>.jpg`，两个尺寸档：`60`（列表行）与 `200`（详情/播放页），
且同一张专辑封面在 `songId@60`、`songId@200`、`al<id>@60`、`al<id>@200` 四个键下各存一份
（`localmeta.saveSongExtras` 预热的就是这四把键）。

**结论：单尺寸 `cover.jpg`（边 200px）。** 依据：

1. **设备高度只有 240px**（逻辑视口 1020×240，1vh = 2.4px）。全应用最大的封面盒子是播放页
   的 152×152px（`ControlPanel` 左列），其余 ≤ 72px（`AlbumCard` 30vh、`PlaylistCard` 28vh、
   列表行 17vh = 40.8px）。**200px 已覆盖最大的盒子并对最小盒子有 4.9 倍余量**，
   没有第二个盒子的尺寸落在 200 与 60 之间需要单独一档。
2. 原两档的真实收益是**列表行网络带宽**（实测 `param=60y60` ≈1.8KB vs `200y200` ≈100KB，55 倍）。
   但那是「浏览时临时缩略图」的成本，**不是「我拥有的这首曲目」的属性** —— 两者被塞进同一个
   `covers/` 才需要「同图两份」。本次拆开（见 0.1.1）。
3. 新布局是**每 track 一个目录**，专辑级去重（同一张专辑 12 首共用一张图）在结构上已经不存在，
   此时「多尺寸」等于「按尺寸数乘整个库的体积」。单尺寸是唯一自洽的选择。

#### 0.1.1 拆成两份数据

| 用途 | 落点 | 生命周期 | 尺寸 |
|---|---|---|---|
| **已下载/已缓存曲目的封面** | `downloads/<id>/cover.jpg`、`cache/<id>/cover.jpg` | 跟随曲目文件（下载永久 / 缓存 LRU） | 200px |
| **浏览时的列表缩略图**（搜索、在线歌单、歌手头像…没有对应本地曲目的那些） | `cache/thumbs/<key>_<size>.jpg` | 可整体清空、不跟随任何曲目 | 60 / 200 |

`cache/thumbs/` 的 key 沿用今天的形态（`<id>@<size>` → 文件名 `<id>_<size>.jpg`，
`id` 可以是 songId、`al<albumId>`、`arp<artistId>`、`ac<userId>`、`pl<playlistId>`）。
**它不是曲目记录的一部分**，存储管理页的「清空封面缓存」清的就是它（+ 已缓存曲目的 cover.jpg）。

### 0.2 歌词：**不转 .lrc，整包进库**

现状 `lrc/<id>.json` = `{l, t, pm, y}`：`l` 原文 LRC、`t` 翻译 LRC、`y` YRC 逐字原文、`pm` 纯音乐标记。
四个字段**已经是原始 LRC/YRC 文本**，只是被 JSON 打成一个包。

**结论：保持这一个 JSON 包（`{v, lrc, tlyric, yrc, pureMusic}`），但不落文件 ——
存在 `track_lyric` 表里，一行一首。** 依据：

1. **`.lrc` 装不下现有数据的三样东西**：逐字 YRC（`y`，实测单首 10284 字符）、翻译轨（`t`）、
   纯音乐标记（`pm`）。要转就变成每首 3 个文件，而从「每 track 一个目录」进一步变成
   「一次播放要写三个文件」—— 每个文件都是一次 fork。
2. **解析成本不构成理由**：`parseLrc`/`parseYrc` 对单首是微秒级，且结果在 `lyric.js` 里按会话缓存
   （`cache[songId]`），一整个播放会话只解析一次。为「省解析」而存预解析结构是把稳定格式换成
   易碎格式，赔本。
3. **`.lrc` 唯一的优势是外部工具可读**，而它已被无损保留：那个 JSON 的 `lrc` 字段就是标准 LRC
   原文，`sqlite3 local_index.db "select v from track_lyric where id=1" | jq -r .lrc` 一行就能导出，
   零解析风险。

## 1. 索引库：为什么用 SQLite

### 1.1 现有矛盾

旧实现是「一张表一个 JSON 文件，整表读写」：`store/local_index.json` 62KB、
`local_playlists.json` 63KB、`cache_meta.json` 37KB。写一次任意一条 = **重写整份文件**。

**这次要动的正是「小表多行」那部分**：曲目索引、歌单索引、歌手资料 —— 条目多、单条小、
按 id 增删改。整表重写在它们身上是纯浪费，SQLite 的行级 upsert 恰好对上。
**也包括**「每 5~15 秒整份重写的小快照」（播放状态、播放历史）与每曲元数据/歌词 ——
它们的麻烦不是库规模，而是写入时机（切歌/暂停/下载完成），见 §1.2。

### 1.2 访问模型（关键约束）

通道 = **原生 `sqlite3` 模块**（`import('sqlite3')` → `new Database()`），不是 CLI。
CLI 每次调用都是一次 fork（真机 92~139ms），而且 SQL 不能走命令行参数（会被代码页转换，
中文变乱码），只能写临时 `.sql` 文件再 `.read`。

本层固定为 **「boot 时索引表整表灌内存 + 写穿」**：

- 读：`open()` 时把六张索引表导出 → 内存对象。**此后索引查询都在内存里**，不再查库。
  文档表（`kv` / `track_meta` / `track_lyric`）按 key 直查，不预载。
- 写：`INSERT ... ON CONFLICT DO UPDATE` 单行 upsert，微秒级，**代价与库规模无关**。
- 批量：一批改动包在一条 `BEGIN; ...; COMMIT;` 里。
- **不在任何轮询路径上读库**（`fetcher` 的 300ms 进度轮询只能用 `fs.stat`，规则不变）。

### 1.3 表结构

```sql
CREATE TABLE album (
  id      INTEGER PRIMARY KEY,
  name    TEXT NOT NULL DEFAULT '',
  cover   TEXT NOT NULL DEFAULT '',
  pub     INTEGER NOT NULL DEFAULT 0     -- 发行时间（ms）
);

CREATE TABLE artist (
  id      INTEGER PRIMARY KEY,
  name    TEXT NOT NULL DEFAULT '',
  avatar  TEXT NOT NULL DEFAULT '',      -- 头像 URL（原 store/artist_meta.json）
  av_at   INTEGER NOT NULL DEFAULT 0     -- 头像记录时间
);

CREATE TABLE track (
  id        INTEGER PRIMARY KEY,
  name      TEXT NOT NULL DEFAULT '',
  alias     TEXT NOT NULL DEFAULT '',    -- JSON 数组（别名）
  album_id  INTEGER NOT NULL DEFAULT 0,
  duration  INTEGER NOT NULL DEFAULT 0,  -- ms
  pub       INTEGER NOT NULL DEFAULT 0,
  track_no  INTEGER NOT NULL DEFAULT 0,
  disc      TEXT    NOT NULL DEFAULT '',
  pop       INTEGER NOT NULL DEFAULT 0,
  fee       INTEGER NOT NULL DEFAULT 0,
  cover     TEXT    NOT NULL DEFAULT '', -- 封面 URL 快照
  -- 曲目自身的落盘状态（下载/缓存共用一张曲目表，靠下面两列区分）
  dl_origin INTEGER NOT NULL DEFAULT 0,  -- 0=无 1=user 2=playlist（原 bpncm_dl_origin）
  added_at  INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE track_artist (          -- 多对多：曲目 ↔ 歌手（顺序即展示顺序）
  track_id  INTEGER NOT NULL,
  artist_id INTEGER NOT NULL,
  ord       INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (track_id, artist_id)
);
CREATE INDEX idx_track_artist_artist ON track_artist(artist_id);

CREATE TABLE playlist (
  id        INTEGER PRIMARY KEY,        -- 网易云歌单 id
  name      TEXT NOT NULL DEFAULT '',
  cover     TEXT NOT NULL DEFAULT '',
  creator   TEXT NOT NULL DEFAULT '',
  track_cnt INTEGER NOT NULL DEFAULT 0, -- 远端总数
  base_ids  TEXT NOT NULL DEFAULT '',   -- JSON 数组：拉取基线（A/D 差异判定）
  remote_ids TEXT NOT NULL DEFAULT '',  -- JSON 数组：最近一次远端快照
  pulled_at INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE playlist_track (        -- 该歌单「本地认为属于它」的曲目
  playlist_id INTEGER NOT NULL,
  track_id    INTEGER NOT NULL,
  ord         INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (playlist_id, track_id)
);
CREATE INDEX idx_playlist_track_track ON playlist_track(track_id);

-- ---- 文档表（原先都是 data/ 下的 JSON 文件）----
CREATE TABLE kv (                    -- 原 config.json / cookie.json / state.json / history.json
  k TEXT PRIMARY KEY,                -- ncm_settings / ncm_cookies / bpncm_player_state / bpncm_playhist
  v TEXT NOT NULL DEFAULT '',
  t INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE track_meta (            -- 原 <track>/metadata.json
  id    INTEGER NOT NULL,
  kind  INTEGER NOT NULL,            -- 1 = downloads（用户下载） 2 = cache（播放缓存）
  v     TEXT NOT NULL DEFAULT '',
  t     INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (id, kind)
);

CREATE TABLE track_lyric (           -- 原 <track>/lyrics.json
  id INTEGER NOT NULL,
  v  TEXT NOT NULL DEFAULT '',
  t  INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (id)
);

PRAGMA user_version = 2;
```

`track_meta.kind` 区分两条媒体通道：同一个 songId 可能同时在 `downloads/` 与 `cache/` 下，
元数据（尤其 `u`=lastUsed）不能互相覆盖。

## 2. 目录契约（`src/utils/paths.js` 是唯一真源）

```
data/
  local_index.db              唯一的数据库：索引表 + kv + 曲目元数据/歌词（§1.3）
  cookie.txt                  调试通道：从 PC 递一份会话进来（启动时导入一次，导入后进库）
  ncm_ck.txt                  curl 登录用的会话 jar（curl 自己写，我们只读）
  downloads/<track_id>/
      track.mp3 | track.flac  音频（扩展名由直链回包 type 定）
      track.mp3.part          下载中的续传残片（.part / .part.cur）
      cover.jpg               封面（单尺寸 200px）
  cache/<track_id>/
      track.mp3 | track.flac
      track.mp3.part
      cover.jpg
  cache/thumbs/<key>_<size>.jpg   浏览缩略图（60/200，可整体清空）
```

**没有 `metadata.json` / `lyrics.json` / `config.json` / `state.json` / `history.json`** ——
它们都是 `local_index.db` 里的行。理由见开头「两条硬规矩」：写文本文件必须借 shell，
一次就是一次 fork。

**`storage/` 目录彻底退役**（不再创建）。`utils/store.js` 现在的实现是 `kv` 表，
不是文件；迁移脚本只负责把旧 `storage/preferences.json` 读进来。

### 2.1 不变式

- 一个 `track_id` 在一个根目录（`downloads/` 或 `cache/`）下**只有一个音频文件**：
  换音质时先把新文件下成 `.part`，下满再 `mv` 顶替，并删掉另一扩展名的旧文件。
- **正式路径永远是完整文件**：`.part` 不会被当成命中（`hitIn` 仍加 `> 30KB` 判定）。
- `downloads/` 下同时存在一曲 → 删掉 `cache/` 下同 id 的目录（原语义保留：同一首不留两份）。
- `cover.jpg` 可缺失：缺了当作「没有」，不影响音频本身。元数据/歌词缺失同理（库里没有行）。
- 删曲目 = 删整个 `<track_id>/` 目录（`fs.rm` 递归，原生调用）+ 删库里对应的元数据行。

### 2.2 迁移判据

`layoutVersion` 记在 **`kv` 表的 `ncm_settings` 行**里（不是 config.json）。当前值 **2**。
`< 2` 才跑迁移，成功才写回；失败保持旧版本、下次启动重试（迁移本身幂等）。

### 3.1 写入范围（互斥，不得跨）

- **Lead**：`utils/paths.js`、`utils/db.js`、`utils/media.js`、`utils/config.js`、`utils/boot.js`、`docs/存储重构.md`、UI 调用点

- **T3**：`utils/migrate.js`、`docs/*.md`（除本文件）、`AGENTS.md`

### 3.2 硬约束（平台坑，改这些文件必须遵守）

- **文本数据一律进 SQLite**（`utils/db.js`）。不要写 `writeTextFile` 之类的 shell 通道：
  平台 `fs` 无写入接口，写文件只能借 shell 重定向，一次一次 fork（真机 92~139ms）。
- **数据库用原生 `sqlite3` 模块**，不要用 `sqlite3` CLI（每次一次 fork + 临时 `.sql` 文件）。
- `process.exec` **不解析命令串**，必须 `/bin/sh -c`；后台命令必须 `>/dev/null 2>&1`。
  它现在只用于 curl 传输、`du`/`df` 统计、迁移的批量 `mv`，以及 curl 的 cookie jar。
  exec 的 fork 成本与 shell 纪律见 [`docs/应用内系统访问能力_2026-10-10.md`](../../../docs/应用内系统访问能力_2026-10-10.md)。
- 轮询只能用 `fs.stat` / `fs.exists`（native，不 fork），绝不能用 exec。
- 建目录/删目录走 `fs.mkdir` / `fs.rm`（**都递归**，原生调用，不需要 `-p` / `-rf`）。
- 所有函数**不抛异常**：失败给安全默认值并记日志。
- 注释里不要出现 `*/`。

## 4. 从旧布局迁移

`utils/migrate.js` 在 boot 时跑一次，`layoutVersion` 记在 **`kv` 表的 `ncm_settings` 行**里
（当前 **2**，旧为 1）。判据 `layoutVersion < 2` → 执行迁移 → 成功才写回 `2`（失败下次启动重试）。

两段独立执行：**文件搬家**（音频/封面/缩略图，走批量 shell `mv`/`cp`，一次 exec 搬几百个）
与**数据搬运**（歌词/元数据/索引/配置/会话，写 SQLite，不进 shell）。

| 旧 | 新 |
|---|---|
| `music/<id>.mp3\|flac` | `downloads/<id>/track.<ext>` |
| `music/` 同 id 的封面 `covers/<id>_200.jpg`（若有） | `downloads/<id>/cover.jpg` |
| `cache/<id>.mp3\|flac` | `cache/<id>/track.<ext>` |
| `lrc/<id>.json` `{l,t,pm,y}` | `track_lyric` 表 `{v:1, lrc, tlyric, yrc, pureMusic}` |
| `store/local_index.json` | `track` / `album` / `artist` / `track_artist` |
| `store/local_playlists.json` | `playlist` / `playlist_track` |
| `store/cache_meta.json` | `track_meta`（kind=1，用户下载） |
| `store/artist_meta.json` | `artist.avatar` / `artist.av_at` |
| storage `bpncm_dl_origin` | `track.dl_origin` |
| storage `bpncm_playcache_meta` | `track_meta`（kind=2，播放缓存） |
| storage `ncm_settings` | `kv` 的 `ncm_settings` 行 |
| storage `ncm_cookies` | `kv` 的 `ncm_cookies` 行 |
| storage `bpncm_player_state` | `kv` 的 `bpncm_player_state` 行 |
| storage `bpncm_playhist` | `kv` 的 `bpncm_playhist` 行 |
| `covers/*.jpg` | `cache/thumbs/`（改名即可，键形态不变） |

迁移要求：
- **只搬不改源**：搬完不删 `music/` `cache/` 旧文件（缓存可再生，留给用户手动清；
  下载文件在 `mv` 成功后才算搬走）。
- 幂等：中途失败重跑不会产出 `downloads/<id>/track.mp3` 与 `downloads/<id>/track.flac` 并存；
  库里已有行（`track_lyric` 该 id / `track_meta` 该 id+kind / `kv` 该 key）就跳过，不覆盖。
- 每一步只记日志不抛；单首失败不阻塞其余。

## 5. 自检

```bash
# 结构自检（不需要设备）
node scripts/storage_selftest.mjs      # 真实 fs + 真 sqlite，把 src/utils 原样跑一遍
python scripts/theme_verify.py         # 现有六道
python scripts/check_unused_imports.mjs
bash scripts/build.sh                  # 便携 Node18 构建

# 设备核对（迁移后）
D=/userdisk/secondary/miniapp/data/mini_app/pkg/8000200708310039/data
devctl run "ls $D; ls $D/downloads | head"
devctl run "sqlite3 $D/local_index.db .tables; sqlite3 $D/local_index.db 'select count(*) from track'"
```

预期：`data/` 下只剩 `cookie.txt ncm_ck.txt local_index.db downloads/ cache/`；
`.tables` 列出 `album artist kv playlist playlist_track track track_artist track_lyric track_meta`。
