# 下载引擎

下载与播放缓存共用一套传输与调度，但目录、元数据、生命周期分开。改下载逻辑前先读 [`src/services/player/download.js`](../src/services/player/download.js) 头部与 `fetcher.js` / `scheduler.js` 注释。目录契约见 [`存储重构.md`](存储重构.md) §2，路径一律从 [`../src/core/infra/paths.js`](../src/core/infra/paths.js) 取。

## 一、两条通道与两类文件

| kind | 谁产生 | 音质 | 目录 | 淘汰 | 出现在「本地下载」 |
|---|---|---|---|---|---|
| `cache` | 播放时自动（play 通道） | 播放音质 | `$dataDir/cache/<id>/` | 受「缓存上限」按播放顺序 LRU | 否 |
| `download` | 用户主动（batch 通道） | 下载音质 | `$dataDir/downloads/<id>/` | 永久保留 | 是 |

每 track 一个目录，目录内只有文件：`track.mp3` | `track.flac`（扩展名由直链回包 `type` 定）、
`track.*.part(.cur)` 续传残片、`cover.jpg`（单尺寸 200px）。
**元数据与歌词不在这层**：它们在 `state.db`（状态库）的 `track_meta` / `track_lyric` 表里
（由 [`../src/services/player/media.js`](../src/services/player/media.js) 统一读写）——
平台 `fs` 没有写接口，写 JSON 文件只能 fork 一次 shell（真机 92~139ms）。

- **play 通道**（`ensureCached`）：最新请求优先，新请求作废旧的等待者。
- **batch 通道**（`downloadSongs`）：FIFO、不淘汰、重试不丢；播放通道优先调度，整体单并发（不跟流播抢带宽）。
- 下载完成会删掉同 id 的 cache 副本；播放请求可以提权 batch 项，但**不改 kind**。
- 去重有三层：inflight / ensureWait（播放侧包装）、waiting 队列、batch 队列；后到的请求搭车或提权，避免同一首下两遍。

**音质档位**（`quality.js`）只影响解析直链时传的 `level`，与通道/目录无关：

- 5 档：标准 / 较高 / 极高 / 无损 / Hi-Res；`config.playQuality` 与 `config.downloadQuality` 各自独立（上表就是「谁用哪档」）。
- 逐档降级、最低 128k 兜底；`hires` 链里带 `lossless`（有会员无超级会员时仍能拿无损）。
- 服务端可能**静默降级**：没权益/曲目没有高码资源时回 mp3；回包 `d.level` 只是标签、**不可靠**（24bit 与 16bit flac 都标 `lossless`）。判实际拿到什么只看 `d.type` + `d.br`。接口参数约束见 [`运行时API参考.md`](运行时API参考.md) 第 11 节。
- 元数据里的 `q` 记的是**请求档**，所以「降级拿到的低码率」会永久视为达标 —— 想真升质要先删再下（取舍见 `download.js` 的 `metaSatisfies` 注释）。

### 1.1 提交协议与退出收尾（2026-11 稳定性改动）

下载的「文件」与「元数据」不再允许分家：

- **开始下载前**先写基础元数据（`cache.begin`）：歌名/歌手/时长/封面 + `p`（本次档位）+
  `z`（预期大小）+ `f`（下载前盘上有没有旧文件）。这样任何时刻退出，都不会出现
  「有歌、没名字」；`z`/`p` 也让启动对账能认出已经下满的残片。
- **下载完成**写完成态（`cache.put`）：实际码率 `b` / 容器 `y` / 档位 `q`，并清 `p`/`z`。
  写库失败重试一次；仍失败只记日志（文件是真相，启动对账会补），**不把下载判失败**。
  升级时 `begin` 不碰旧的 `b/y/q`，避免「升级失败」被误判成已升级。
- **判重**必须同时满足 `metaReady`（有歌名、无 `p`、有 `q/y/b`）与 `metaSatisfies`（档位够）。
  缺元数据的旧行先就地补（不重新拉音频）；只有「只剩 `p`、又没有档位/码率证据」的行
  才重下一次，成功后 `q` 就补齐了。
- **退出**（`download.stopForExit`）：取消批量队列 + 清播放通道排队项 +
  `fetcher.stopFetching()` 杀掉活跃 curl，最多等 800ms。`.part` 与 `dl_pending`
  （批量队列快照）保留；`index.vue` 的退出链先调它，再暂停播放、关应用。
- **下次启动**（`boot`）：`reconcileDownloads()` 先对账（补元数据、把已下满的 `.part`
  转正、清掉没有 `.part` 的 `.rc/.cur`，不联网），然后 `resumePendingDownloads()`
  延迟续传上次的队列（离线则保留到下次）。
- **取消**（下载队列页的两个入口，都是两次点按确认）：左栏「取消全部」→ `cancelDownload()`
  （整批作废：排队中的按已取消结算，正在下的在分片边界停下）；每行右侧的取消按钮 →
  `cancelTask(id)`（只中断这一首）。`.part` 与元数据保留，重新下载会续传。
- **防双写**：开始下载前若发现同一 `.part` 已存在，先 `pkill` 掉上一进程可能残留的 curl；
  完整残片转正前也先杀一次，避免 `mv` 之后旧进程继续往同一个 inode 追加。

PC 侧回归：`node scripts/download_selftest.mjs`（平台 shim + 真 sqlite，覆盖 begin/put、
启动对账、跳判重与退出收尾）。

## 二、传输：整文件优先 + 分片兜底

`fetchToFile()` 以 `wholeFetch` 为主，失败回退 `curlFetch`：

- 后台拉起 `curl -C -` 写 `.part`，同时写 rc 文件；JS 侧轮询进度。
- 两条通道共用同一个 `.part`，对外签名不变。`.part` 与新布局的对应关系：`<id>/track.<ext>.part`
  （换档位重下时是 `.part.cur`），正式路径 `track.<ext>` 只在文件下满后由 `mv` 出现。
- 取消：完成优先于取消；取消时 `pkill -9` 对应 curl，等 250ms 释放文件句柄再返回。
- 整文件通道失败（rc/HTTP 异常、低速、超时）才回退分片；分片有自适应片长、换节点与重试上限。

### 三条死线（改这块前必看）

1. **后台命令必须 `>/dev/null 2>&1`**：不重定向的话 `process.exec` 会继承 stdout 管道，等到后台进程结束才返回（整个方案的前提）。exec 的 fork 成本与 shell 纪律见 [`docs/应用内系统访问能力_2026-10-10.md`](../../../docs/应用内系统访问能力_2026-10-10.md)。
2. **轮询只能用 `fs.stat` / `fs.exists`（native，零 fork）**：绝不能用 exec（S7 实测一次 92~139ms）。
3. **完成优先于取消**：轮询里先查 rc 再查 `shouldAbort`；否则「文件刚好下完 + 用户点取消」会被误判成已取消，上层不 promote，白丢一个完整 `.part`。

## 三、整文件通道参数

| 常量 | 值 | 说明 |
|---|---|---|
| `POLL_MS` | 300 | 进度轮询间隔（`fs.stat`，零 fork） |
| `WHOLE_MAX_TRY` | 3 | 整轮重试上限；`-C -` 会接着下，不丢进度 |
| `WHOLE_MAX_TIME` | 600 | 单轮最长秒数 |
| `WHOLE_SPEED_LIMIT_BPS` | 16K | 低速阈值（比 curl 分片通道宽松，避免慢节点反复重启整轮） |
| `WHOLE_SPEED_TIME_SEC` | 30 | 低于限速持续多久后中断 |
| `POLL_TICK_MAX` | 2400 | 轮询空转上限（2400 × 300ms = 12 分钟，兜住 rc 文件丢失） |

分片通道参数见 `fetcher.js` 顶部：`CHUNK_MAX` 4MB、`LOW_SPEED_BPS` 64K、`SPEED_LIMIT_BPS` 48K、`MAX_TRY_PER_CHUNK` 3、`MAX_NODE_SWITCH` 3 等。

## 四、性能参考（设备实测）

完整 5 轮实测数据（局域网与公网、分片 vs 整文件、`http.request`/`http.download`/curl 对比）在 [`docs/fetch通道速度实测_2026-10-17.md`](../../../docs/fetch通道速度实测_2026-10-17.md)，此处只留与下载引擎设计直接相关的结论：

- **片越小越慢**（2026-10-17 局域网复测：10MB 整文件 1.09s、4MB 片 2.56s、512KB 片 4.61s，固定片长 2 exec/片），整文件优先、分片兜底。
- `process.exec` 裸 fork S7 实测 92~139ms/次（早期一版记录 48~52ms，偏低），每片两次 exec 就是两三百毫秒固定开销。

结论：**片越小越慢**，不要把片调小；整文件优先、分片兜底。另测得 `process.exec` 裸 fork
S7 实测 **92~139ms/次**（早期一版记录 48~52ms，偏低），每片两次 exec 就是两三百毫秒固定开销。

> 2026-10-17 局域网复测（9~10MB/s，固定片长、2 exec/片）：整文件 1.09s、4MB 片 2.56s、512KB 片 4.61s。
> 上表的 5 片是自适应片长策略，不能与固定片长直接对比；片数/连接数比片大小更关键，快链路上分片开销占比更高。

引用任何速度结论前必须记录测量条件（URL/服务器、信号、窗口大小、并发数）；窗口小于 16MB 会严重低估吞吐。

低速换节点阈值 `LOW_SPEED_BPS = 64KB/s` 偏宽：挂在 1.5MB/s 的差节点上可能不触发换节点；调整前先测真实链路。

## 五、下载归属标记（本地下载分类用）

`downloadSongs(songs, opts)` 的 `opts.origin` 决定完成后写哪种归属（`dlorigin.js`，落库为 `track.dl_origin` 列）：

- `manual`（默认）：播放器下载键、专辑/歌手/搜索、列表多选下载 → `user`（`track.dl_origin = 1`）。
- `playlist`：只在已索引歌单的「下载全部」/ 同步/自动同步 → `playlist`（`dl_origin = 2`）；
  跳过已存在文件时只给无标记的补 `user`，不把用户已有文件认领成歌单归属。

归属只影响「单曲下载 / 遗留歌曲 / 歌单内」的分类，不影响文件行为。分类与策略 A 见
[`本地下载.md`](本地下载.md)。

## 六、测量约定

- 引用任何速度结论前必须记录测量条件（URL/服务器、信号、窗口大小、并发数）；窗口小于 16MB 会严重低估吞吐。
- 不要为「播放卡顿」优化带宽：现有记录里没有「流播卡顿」现象，实际观察到的是起播慢；带宽实测有富余。
