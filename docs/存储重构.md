# 应用存储重构：目录契约、索引库与两项格式自评估

> 状态：**实施中**（分支 `refactor/storage-layout`）。本文是这次重构的**唯一契约**：
> 所有模块都按 §2 / §3 / §4 的路径与字段实现，不在各自文件里另拼路径。
>
> 目标布局（用户提出）：
>
> ```
> data/
>     config.json（应用配置）
>     local_index.db（表：album/artist/track/playlist）
>     downloads/<track_id>/{track.mp3|flac, cover.jpg, lyrics.json, metadata.json}
>     cache/<track_id>/{track.mp3|flac, cover.jpg, metadata.json}
> ```

---

## 0. 两项自评估的结论（先给答案）

### 0.1 封面：**不需要多个尺寸**，`covers/` → `cover.jpg`

现状是 `covers/<key>_<size>.jpg`，两个尺寸档：`60`（列表行）与 `200`（详情/播放页），
且同一张专辑封面在 `songId@60`、`songId@200`、`al<id>@60`、`al<id>@200` 四个键下各存一份
（`localmeta.saveSongExtras` 预热的就是这四把键）。

**结论：单尺寸 `cover.jpg`（边 200px）。** 依据：

1. **设备高度只有 240px**（逻辑视口 1020×240，1vh = 2.4px）。全应用最大的封面盒子是播放页
   的 152×152px（`ControlPanel` 左列），其余 ≤ 72px（`AlbumCard` 30vh、`PlaylistCard` 28vh、
   列表行 17vh = 40.8px）。**200px 已覆盖最大的盒子并对最小盒子有 4.9 倍余量**，
   没有第二个盒子的尺寸落在 200 与 60 之间需要单独一档。
2. 原两档的真实收益是**列表行网络带宽**（实测 `param=60y60` ≈1.8KB vs `200y200` ≈100KB，55 倍）。
   但那是「浏览时临时缩略图」的成本，**不是「我拥有的这首曲目」的属性** —— 两者被塞进同一个
   `covers/` 才需要「同图两份」。本次拆开（见 0.1.1）。
3. 新布局是**每 track 一个目录**，专辑级去重（同一张专辑 12 首共用一张图）在结构上已经不存在，
   此时「多尺寸」等于「按尺寸数乘整个库的体积」。单尺寸是唯一自洽的选择。

#### 0.1.1 拆成两份数据

| 用途 | 落点 | 生命周期 | 尺寸 |
|---|---|---|---|
| **已下载/已缓存曲目的封面** | `downloads/<id>/cover.jpg`、`cache/<id>/cover.jpg` | 跟随曲目文件（下载永久 / 缓存 LRU） | 200px |
| **浏览时的列表缩略图**（搜索、在线歌单、歌手头像…没有对应本地曲目的那些） | `cache/thumbs/<key>_<size>.jpg` | 可整体清空、不跟随任何曲目 | 60 / 200 |

`cache/thumbs/` 的 key 沿用今天的形态（`<id>@<size>` → 文件名 `<id>_<size>.jpg`，
`id` 可以是 songId、`al<albumId>`、`arp<artistId>`、`ac<userId>`、`pl<playlistId>`）。
**它不是曲目记录的一部分**，存储管理页的「清空封面缓存」清的就是它（+ 已缓存曲目的 cover.jpg）。

### 0.2 歌词：**不转 .lrc，保持单个 `lyrics.json`**

现状 `lrc/<id>.json` = `{l, t, pm, y}`：`l` 原文 LRC、`t` 翻译 LRC、`y` YRC 逐字原文、`pm` 纯音乐标记。
四个字段**已经是原始 LRC/YRC 文本**，只是被 JSON 打成一个包。

**结论：保持 `lyrics.json`，不拆成 `.lrc`。** 依据：

1. **`.lrc` 装不下现有数据的三样东西**：逐字 YRC（`y`，实测单首 10284 字符）、翻译轨（`t`）、
   纯音乐标记（`pm`）。要转就变成每首 3 个文件（`lyrics.lrc` + `lyrics.zh.lrc` + 逐字格式），
   在「每 track 一个目录」下文件数从 1 涨到 3，原子性从「一次写」变成「三次写」。
2. **解析成本不构成理由**：`parseLrc`/`parseYrc` 对单首是微秒级，且结果在 `lyric.js` 里按会话缓存
   （`cache[songId]`），一整个播放会话只解析一次。为「省解析」而存预解析结构是把稳定格式换成
   易碎格式，赔本。
3. **`.lrc` 唯一的优势是外部工具可读**，而它已被无损保留：`lyrics.json` 的 `lrc` 字段就是
   标准 LRC 原文，PC 侧 `jq -r .lrc` 一行就能导出，零解析风险。

> 若将来真有「把 downloads/ 拷到 PC 直接被播放器识别」的需求，再在**下载目录**额外落一份
> `lyrics.lrc` 纯导出视图即可（`lyrics.json` 仍是唯一真相），本次不做。

## 1. 索引库：为什么这次上 SQLite

### 1.1 现有矛盾

`docs/存储层.md` 用的是「一张表一个 JSON 文件，整表读写」：`store/local_index.json` 62KB、
`local_playlists.json` 63KB、`cache_meta.json` 37KB。写一次任意一条 = **重写整份文件**
（一次 fork + 62KB 写）。而 `docs/存储层.md` 自己也写明：

> 设备上 `/usr/bin/sqlite3` 是 3.39.2，可用；但每次写要走 fork，适合「小表多行」，
> 不适合「每 5 秒一次的快照」。

**这次要动的正是「小表多行」那部分**：曲目索引、歌单索引、歌手资料 —— 条目多、单条小、
按 id 增删改。整表重写在它们身上是纯浪费，SQLite 的行级 upsert 恰好对上。
**不含**的是「每 5~15 秒整份重写的小快照」（播放状态、播放历史），它们继续走 JSON 文件。

### 1.2 访问模型（关键约束）

平台**没有原生 sqlite 模块**，只能 `process.exec('/bin/sh', ['-c', 'sqlite3 ...'])`，一次约 50ms。

因此本层固定为 **「boot 时整表灌内存 + 写穿」**：

- 读：`open()` 时一次 `sqlite3 -json` 批量导出各表 → 内存对象。**此后所有查询都在内存里**，
  与今天 `local_index.json` 的读路径同速（`fs.readFile` 级别，不分叉）。
- 写：`INSERT ... ON CONFLICT DO UPDATE` 单条 upsert，一次 fork，**代价与库规模无关**
  （这正是相对 JSON 整表重写的收益）。
- 批量：一批改动包在一条 `BEGIN; ...; COMMIT;` 里，一批只 fork 一次。
- **不在任何轮询/高频路径上读库**（`fetcher` 的 300ms 进度轮询只能用 `fs.stat`，规则不变）。

### 1.3 表结构

```sql
CREATE TABLE album (
  id      INTEGER PRIMARY KEY,
  name    TEXT NOT NULL DEFAULT '',
  cover   TEXT NOT NULL DEFAULT '',
  pub     INTEGER NOT NULL DEFAULT 0     -- 发行时间（ms）
);

CREATE TABLE artist (
  id      INTEGER PRIMARY KEY,
  name    TEXT NOT NULL DEFAULT '',
  avatar  TEXT NOT NULL DEFAULT '',      -- 头像 URL（原 store/artist_meta.json）
  av_at   INTEGER NOT NULL DEFAULT 0     -- 头像记录时间
);

CREATE TABLE track (
  id        INTEGER PRIMARY KEY,
  name      TEXT NOT NULL DEFAULT '',
  alias     TEXT NOT NULL DEFAULT '',    -- JSON 数组（别名）
  album_id  INTEGER NOT NULL DEFAULT 0,
  duration  INTEGER NOT NULL DEFAULT 0,  -- ms
  pub       INTEGER NOT NULL DEFAULT 0,
  track_no  INTEGER NOT NULL DEFAULT 0,
  disc      TEXT    NOT NULL DEFAULT '',
  pop       INTEGER NOT NULL DEFAULT 0,
  fee       INTEGER NOT NULL DEFAULT 0,
  cover     TEXT    NOT NULL DEFAULT '', -- 封面 URL 快照
  -- 曲目自身的落盘状态（下载/缓存共用一张曲目表，靠下面两列区分）
  dl_origin INTEGER NOT NULL DEFAULT 0,  -- 0=无 1=user 2=playlist（原 bpncm_dl_origin）
  added_at  INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE track_artist (          -- 多对多：曲目 ↔ 歌手（顺序即展示顺序）
  track_id  INTEGER NOT NULL,
  artist_id INTEGER NOT NULL,
  ord       INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (track_id, artist_id)
);
CREATE INDEX idx_track_artist_artist ON track_artist(artist_id);

CREATE TABLE playlist (
  id        INTEGER PRIMARY KEY,        -- 网易云歌单 id
  name      TEXT NOT NULL DEFAULT '',
  cover     TEXT NOT NULL DEFAULT '',
  creator   TEXT NOT NULL DEFAULT '',
  track_cnt INTEGER NOT NULL DEFAULT 0, -- 远端总数
  base_ids  TEXT NOT NULL DEFAULT '',   -- JSON 数组：拉取基线（A/D 差异判定）
  remote_ids TEXT NOT NULL DEFAULT '',  -- JSON 数组：最近一次远端快照
  pulled_at INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE playlist_track (        -- 该歌单「本地认为属于它」的曲目
  playlist_id INTEGER NOT NULL,
  track_id    INTEGER NOT NULL,
  ord         INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (playlist_id, track_id)
);
CREATE INDEX idx_playlist_track_track ON playlist_track(track_id);

PRAGMA user_version = 1;
```

`cache_meta`（播放缓存的 LRU 元数据）**不进 DB**：它每切一首歌就改一次，是 1.2 节排除掉的
「高频小块」，落 `cache/<id>/metadata.json`（与曲目目录同生共死，删目录即删元数据）。

## 2. 目录契约（`src/utils/paths.js` 是唯一真源）

```
data/
  config.json                 应用配置（原 storage 的 ncm_settings，整份 JSON）
  cookie.json                 登录 Cookie（原 storage 的 ncm_cookies）
  state.json                  播放会话快照（原 storage 的 bpncm_player_state；高频小块）
  history.json                播放历史（原 storage 的 bpncm_playhist；高频小块）
  cookie.txt                  adb 递会话用的导入通道（保留，导出/导入用）
  local_index.db              SQLite 索引库（§1.3）
  downloads/<track_id>/
      track.mp3 | track.flac  音频（扩展名由直链回包 type 定）
      track.mp3.part          下载中的续传残片（.part / .part.cur）
      cover.jpg               封面（单尺寸 200px）
      lyrics.json             {v, lrc, tlyric, yrc, pureMusic}
      metadata.json           {n,a,b,y,q,d,c,origin,addedAt}
  cache/<track_id>/
      track.mp3 | track.flac
      track.mp3.part
      cover.jpg
      metadata.json           {n,a,b,y,q,d,u,p,t}（u=lastUsed，p=续传档位标记）
  cache/thumbs/<key>_<size>.jpg   浏览缩略图（60/200，可整体清空）
```

**`storage/` 目录彻底退役**（不再创建），`utils/store.js` 只在迁移脚本里保留读取能力。

### 2.1 不变式

- 一个 `track_id` 在一个根目录（`downloads/` 或 `cache/`）下**只有一个音频文件**：
  换音质时先把新文件下成 `.part`，下满再 `mv` 顶替，并删掉另一扩展名的旧文件。
- **正式路径永远是完整文件**：`.part` 不会被当成命中（`hitIn` 仍加 `> 30KB` 判定）。
- `downloads/` 下同时存在一曲 → 删掉 `cache/` 下同 id 的目录（原语义保留：同一首不留两份）。
- `cover.jpg` / `lyrics.json` / `metadata.json` 都可缺失：缺了当作「没有」，不影响音频本身。
- 删曲目 = 删整个 `<track_id>/` 目录（一次 `rm -rf`），连带封面/歌词/元数据一起走。

- **T3**：`utils/migrate.js`、`docs/*.md`（除本文件）、`AGENTS.md`

### 3.2 硬约束（平台坑，改这些文件必须遵守）

- `process.exec` **不解析命令串**，必须 `/bin/sh -c`；后台命令必须 `>/dev/null 2>&1`。
- 轮询只能用 `fs.stat` / `fs.exists`（native，不 fork），绝不能用 exec。
- 写文本走 `fsutil.writeTextFile`（`printf` 重定向 + `mv -f` 原子替换，超 60KB 自动分片）。
- 平台 `fs` **无写入接口**；读走原生 `fs.readFile`。
- 所有函数**不抛异常**：失败给安全默认值并记日志。
- 注释里不要出现 `*/`。

## 4. 从旧布局迁移

`utils/migrate.js` 在 boot 时跑一次，`config.json` 里记 `layoutVersion`（当前 **2**，旧为 1）。
判据 `layoutVersion < 2` → 执行迁移 → 成功才写回 `layoutVersion: 2`（失败下次启动重试）。

| 旧 | 新 |
|---|---|
| `music/<id>.mp3\|flac` | `downloads/<id>/track.<ext>` |
| `music/` 同 id 的封面 `covers/<id>_200.jpg`（若有） | `downloads/<id>/cover.jpg` |
| `cache/<id>.mp3\|flac` | `cache/<id>/track.<ext>` |
| `lrc/<id>.json` `{l,t,pm,y}` | `downloads/<id>/lyrics.json` `{v:1, lrc, tlyric, yrc, pureMusic}` |
| `store/local_index.json` | `track` / `album` / `artist` / `track_artist` |
| `store/local_playlists.json` | `playlist` / `playlist_track` |
| `store/cache_meta.json` | `downloads/<id>/metadata.json` |
| `store/artist_meta.json` | `artist.avatar` / `artist.av_at` |
| storage `bpncm_dl_origin` | `track.dl_origin` |
| storage `bpncm_playcache_meta` | `cache/<id>/metadata.json` |
| storage `ncm_settings` | `config.json` |
| storage `ncm_cookies` | `cookie.json` |
| storage `bpncm_player_state` | `state.json` |
| storage `bpncm_playhist` | `history.json` |
| `covers/*.jpg` | `cache/thumbs/`（改名即可，键形态不变） |

迁移要求：
- **只搬不改源**：搬完不删 `music/` `cache/` 旧文件（缓存可再生，留给用户手动清；
  下载文件在 `mv` 成功后才算搬走）。
- 幂等：中途失败重跑不会产出 `downloads/<id>/track.mp3` 与 `downloads/<id>/track.flac` 并存。
- 每一步只记日志不抛；单首失败不阻塞其余。
