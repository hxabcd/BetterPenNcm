# 存储层：为什么大表不放 storage

本文说明 BPN 的数据落在什么位置、为什么这样分，以及写入通道的一致性约束。判断依据是平台 storage 的实现
行为和真机实测（设备 S7 / 固件 4.23.0）。

## 一、约束：storage 是单文件 KV

平台 `storage`（`libfalcon.so` 的 `JQuick::SharedPreferences`）把**全部 key 写在一个文件**：
`<appdata>/data/storage/preferences.json`。`setStorage` 一次 = 整份文件重写一次，
**写代价 ∝ 全库总量，与这次写的是哪个 key 无关**。

因此「每首一个 key」只是逻辑隔离：所有 key 物理上仍在同一个文件里，存一条 4KB 的歌词要重写整份。
实测写入速度约 0.13ms/KB，147KB 的库单次写 ≈20ms。

## 二、落点

按「体积 × 写频次」分配：大块低频进文件，小块高频留 storage（写文件要走 shell，见第三节）。

| 数据 | 落点 | 当前体积 |
|---|---|---:|
| 歌词（每首一个文件） | `$dataDir/lrc/<songId>.json` | 均值 4.8KB，161 首合计 771KB（2026-10-31 起同文件多存一份 YRC，见下注） |
| 本地索引（歌曲详情 + 歌手/专辑 id） | `$dataDir/store/local_index.json` | ~54KB |
| 歌单本地索引（远端快照 + 拉取状态） | `$dataDir/store/local_playlists.json` | ~63KB |
| 下载元数据（歌名/歌手/码率） | `$dataDir/store/cache_meta.json` | ~37KB |
| 歌手资料（头像 URL） | `$dataDir/store/artist_meta.json` | ~19KB |
| 播放快照 / 播放历史 / 播放缓存元数据 / 设置 / cookie / 下载归属 | **storage**（6 个 key） | ~147KB |

留在 storage 的都是「5~15 秒写一次」的小块：写 147KB 的库 ≈20ms 且不 fork，写文件则要 fork（≈50ms）。
所以目标是「别为一条小数据重写整库」，不是「把所有东西搬出 storage」。

歌词单独散成小文件，是因为它的访问粒度就是单首：写一次/首、读一次/首（`lyricOf(id)`）、删一首删一个文件，
启动时不读。代价是小文件的 4K 块对齐开销（161 个文件约 290KB 的分配增量），换来写入与库规模无关。

> 2026-10-31 起文件多一个 `y` 字段（YRC 逐字原文，逐字接口打通后见 [播放页.md](播放页.md) 第五节）。
> 上表的 771KB 是**只有 LRC 时**的实测值；有逐字的曲目 `y` 会明显变大（实测「きゅうくらりん」YRC 10284 字符，
> 而同一首的 LRC 约 1.5KB），整体体积随「有逐字曲目占比」上升，尚未重新统计。
> 方案不变：写一次/首的粒度没变，`writeJsonAt` 分片阈值 60KB，长歌词仍是一到两片。

## 三、写通道与一致性

- **写入必须走 shell**：平台 `fs` 模块只有 `exists/stat/statfs/readdir/readFile/mkdir/rm`，没有写入接口；
  `global.createFile` 只建空文件。实现见 [`../src/utils/fsutil.js`](../src/utils/fsutil.js) 的 `writeTextFile`。
- **原子替换**：先写 `<path>.tmp`，再 `mv -f` 覆盖。读到的永远是完整一版。
- **分片**：`/bin/sh -c` 的整串命令是**一个 argv**，Linux 单参数上限 128KB，所以按「转义后的字节数」
  在 60KB 处分片（首片 `>`，后续 `>>`，最后一片带 `mv`），**每片一次 exec**。
  本地索引/歌单索引目前落一到两片。
- **合并写**：同一文件一条串行队列，一次在飞；期间来的新版本顶掉旧版本，只落最新一版。
  删除也排在同一条队列里，避免「清空之后被在飞的旧写写回来」。
- **失败只记日志**：没有 storage 兜底。两处都写会让「哪份是真的」变成需要判断的事，
  而这里只有文件是真相；内存里的数据仍在，下一次写会重试。
- 读走 `fs.readFile`（原生、不 fork）。启动链只 `mkdir` 三个目录（`storage/`、`store/`、`lrc/`），不写 storage。

## 四、不做数据迁移

本层只认文件。storage 里若还留着历史 key（`bpncm_local_*`、`bpncm_cache_meta`、`bpncm_artist_meta`、
`bpncm_lrc.*`），既不读也不清 —— 需要保留的由人工搬一次。从旧版本升级时，这四类数据不会自动继承，
表现为「本地下载页有文件但没索引」「歌词缺失」；重装（`miniapp_cli uninstall`）会把 data 目录整个清掉，
`scripts/install.sh` 只在装卸期间暂存 `store/` 与 `lrc/`。

## 五、什么时候需要再换方案

- `preferences.json` 涨到 ~800KB（约 700~800 首仍需高频写的条目），单次写 >100ms 时；
- 或出现「按 id 随机查一条」的真实需求（现在全是整表载入内存，内存里查）。

设备上 `/usr/bin/sqlite3` 是 3.39.2，可用；但每次写要走 fork，适合「小表多行」，
不适合「每 5 秒一次的快照」—— 快照仍应留在 storage。

## 六、核对

```bash
D=/userdisk/secondary/miniapp/data/mini_app/pkg/8000200708310039/data
adb shell "ls $D/lrc | wc -l; ls -l $D/store; ls -l $D/storage/preferences.json"
```

预期：`lrc/` 每首一个 JSON、`store/` 四张表、`preferences.json` 只剩 6 个 key（约 147KB）。
装机脚本的数据备份清单包含 `store/` 与 `lrc/`（`scripts/install.sh`）；
漏掉它们的话，`miniapp_cli uninstall` 之后会出现「文件在、索引没了」。
