# 下载引擎

下载与播放缓存共用一套传输与调度，但目录、元数据、生命周期分开。改下载逻辑前先读 [`src/utils/player/download.js`](../src/utils/player/download.js) 头部与 `fetcher.js` / `scheduler.js` 注释。

## 一、两条通道与两类文件

| kind | 谁产生 | 音质 | 目录 | 淘汰 | 出现在「本地下载」 |
|---|---|---|---|---|---|
| `cache` | 播放时自动（play 通道） | 播放音质 | `$dataDir/cache` | 受「缓存上限」按播放顺序 LRU | 否 |
| `download` | 用户主动（batch 通道） | 下载音质 | `$dataDir/music` | 永久保留 | 是 |

- **play 通道**（`ensureCached`）：最新请求优先，新请求作废旧的等待者。
- **batch 通道**（`downloadSongs`）：FIFO、不淘汰、重试不丢；播放通道优先调度，整体单并发（不跟流播抢带宽）。
- 下载完成会删掉同 id 的 cache 副本；播放请求可以提权 batch 项，但**不改 kind**。
- 去重有三层：inflight / ensureWait（播放侧包装）、waiting 队列、batch 队列；后到的请求搭车或提权，避免同一首下两遍。

**音质档位**（`quality.js`）只影响解析直链时传的 `level`，与通道/目录无关：

- 5 档：标准 / 较高 / 极高 / 无损 / Hi-Res；`config.playQuality` 与 `config.downloadQuality` 各自独立（上表就是「谁用哪档」）。
- 逐档降级、最低 128k 兜底；`hires` 链里带 `lossless`（有会员无超级会员时仍能拿无损）。
- 服务端可能**静默降级**：没权益/曲目没有高码资源时回 mp3；回包 `d.level` 只是标签、**不可靠**（24bit 与 16bit flac 都标 `lossless`）。判实际拿到什么只看 `d.type` + `d.br`。接口参数约束见 [`运行时API参考.md`](运行时API参考.md) 第 11 节。
- 元数据里的 `q` 记的是**请求档**，所以「降级拿到的低码率」会永久视为达标 —— 想真升质要先删再下（取舍见 `download.js` 的 `metaSatisfies` 注释）。

## 二、传输：整文件优先 + 分片兜底

`fetchToFile()` 以 `wholeFetch` 为主，失败回退 `curlFetch`：

- 后台拉起 `curl -C -` 写 `.part`，同时写 rc 文件；JS 侧轮询进度。
- 两条通道共用同一个 `.part`，对外签名不变。
- 取消：完成优先于取消；取消时 `pkill -9` 对应 curl，等 250ms 释放文件句柄再返回。
- 整文件通道失败（rc/HTTP 异常、低速、超时）才回退分片；分片有自适应片长、换节点与重试上限。

### 三条死线（改这块前必看）

1. **后台命令必须 `>/dev/null 2>&1`**：不重定向的话 `process.exec` 会继承 stdout 管道，等到后台进程结束才返回（整个方案的前提）。
2. **轮询只能用 `fs.stat` / `fs.exists`（native，零 fork）**：绝不能用 exec（一次约 48ms）。
3. **完成优先于取消**：轮询里先查 rc 再查 `shouldAbort`；否则「文件刚好下完 + 用户点取消」会被误判成已取消，上层不 promote，白丢一个完整 `.part`。

## 三、整文件通道参数

| 常量 | 值 | 说明 |
|---|---|---|
| `POLL_MS` | 300 | 进度轮询间隔（`fs.stat`，零 fork） |
| `WHOLE_MAX_TRY` | 3 | 整轮重试上限；`-C -` 会接着下，不丢进度 |
| `WHOLE_MAX_TIME` | 600 | 单轮最长秒数 |
| `WHOLE_SPEED_LIMIT_BPS` | 16K | 低速阈值（比 curl 分片通道宽松，避免慢节点反复重启整轮） |
| `WHOLE_SPEED_TIME_SEC` | 30 | 低于限速持续多久后中断 |
| `POLL_TICK_MAX` | 2400 | 轮询空转上限（2400 × 300ms = 12 分钟，兜住 rc 文件丢失） |

分片通道参数见 `fetcher.js` 顶部：`CHUNK_MAX` 4MB、`LOW_SPEED_BPS` 64K、`SPEED_LIMIT_BPS` 48K、`MAX_TRY_PER_CHUNK` 3、`MAX_NODE_SWITCH` 3 等。

## 四、性能参考（设备实测）

测量条件：同一首 10.69MB / 320k，信号约 -15dBm；CDN 与时段不同会有 3~5 倍波动。

| 策略 | 片数 | 墙钟 | 有效速度 |
|---|---|---|---|
| 512KB 片 | 5 | 1990~2118ms | ~4930 KB/s |
| 4MB 片 | 3 | 1406ms | 7426 KB/s |
| 整文件一次 curl | 1 | 949ms | 11002 KB/s |

结论：**片越小越慢**，不要把片调小；整文件优先、分片兜底。另测得 `process.exec` 裸 fork 约 48~52ms/次，每片两次 exec 约 100ms 固定开销。

> 2026-10-17 局域网复测（9~10MB/s，固定片长、2 exec/片）：整文件 1.09s、4MB 片 2.56s、512KB 片 4.61s。
> 上表的 5 片是自适应片长策略，不能与固定片长直接对比；片数/连接数比片大小更关键，快链路上分片开销占比更高。

低速换节点阈值 `LOW_SPEED_BPS = 64KB/s` 偏宽：挂在 1.5MB/s 的差节点上可能不触发换节点；调整前先测真实链路。

## 五、下载归属标记（本地下载分类用）

`downloadSongs(songs, opts)` 的 `opts.origin` 决定完成后写哪种归属（`dlorigin.js`）：

- `manual`（默认）：播放器下载键、专辑/歌手/搜索、列表多选下载 → `user`。
- `playlist`：只在已索引歌单的「下载全部」/ 同步/自动同步 → `playlist`；
  跳过已存在文件时只给无标记的补 `user`，不把用户已有文件认领成歌单归属。

归属只影响「单曲下载 / 遗留歌曲 / 歌单内」的分类，不影响文件行为。分类与策略 A 见
[`本地下载.md`](本地下载.md)。

## 六、探针与测量约定

- 探针工程在工作区 `dev/dl-probe/`（不随本仓库发布），独立 appid、独立 data 目录，不碰用户数据。
- 引用任何速度结论前必须记录测量条件（URL/服务器、信号、窗口大小、并发数）；窗口小于 16MB 会严重低估吞吐。
- 不要为「播放卡顿」优化带宽：现有记录里没有「流播卡顿」现象，实际观察到的是起播慢；带宽实测有富余。
