# 渲染性能

> 本文说明**当前实现**里哪些重渲染被刻意消掉了、用什么机制消掉的、以及为什么这样做。
> 平台层面能做什么动效、哪些属性可插值，见 [平台约束与自检.md](平台约束与自检.md)；播放页几何与组件接口见 [播放页.md](播放页.md)。

设备条件：S7 / 固件 4.23.0 / 1020×240 逻辑视口（1vh = 2.4px）。

## 一、问题形状

这个应用里的重渲染主要不是由用户操作触发的，而是由**广播**触发的：

| 广播源 | 频率 | 订阅方 |
|---|---|---|
| `player.on(fn)` 播放器快照 | 500 ms | 播放页、队列页、主页、NowLyric、NowProgress、LyricBoard、sleeptimer |
| `onDl(fn)` 下载活动 | ~400 ms（节流） | 主页、list、plinfo、album、downloads、dltracks、dlqueue |
| `sleepTimer.on(fn)` 定时播放倒计时 | 1000 ms | 播放页、TimerPanel |
| LyricBoard 自持时钟 | 33 ms | 歌词面板 |

关键在于：**页面被 navTo 压栈后不会卸载**，平台只销毁被弹掉的实例（见 [页面导航.md](页面导航.md)）。所以「进播放页 → 返回主页 → 再进列表」之后，主页、列表、播放页三棵组件树都还活着，上述广播会同时打到所有存活订阅者身上；用户看得见的只有栈顶那一页，其余帧预算全是白花的。

于是优化主线是两条，且必须**同时**做才有意义：

1. **不可见的页面不渲染**——省掉整页重渲染；
2. **可见但内容没变的 tick 也不渲染**——500 ms 的快照里经常一个像素都不会变（时间按秒显示、进度条按 0.1% 量化）。

两条都是「省渲染」而非「省数据」：被跳过的 tick 必须在重新可见、或数值真变了的时候补齐。这条不变式由两个模块保证：`src/utils/ui/vis.js`（可见性真源）与 `src/utils/player/sig.js`（签名判重）。

## 二、可见性真源：`utils/ui/vis.js`

信号来自 `App.onPageLifeCycle` 的 `{page, lifeCycle}`，由 [nav.js](../src/utils/nav.js) 的 `noteLifeCycle` 记账：

| 生命周期 | 处理 |
|---|---|
| `load` | 记入页面栈 `LIVE`，标为可见（新页面一定在最上面） |
| `show` | 标为可见 |
| `hide` | 标为不可见 |
| `unload` | 从 `LIVE` 摘除；**同时把新的栈顶页重新标为可见** |

最后一条是刻意的兜底。若平台在某条路径上只派发 `hide` 而不派发对应的 `show`，被盖住的页会永远停在「不可见」，也就是永远不刷新——那比掉帧严重得多。所以失效方向必须是 fail-open：

- **默认可见**：只有明确收到 `hide` 才置为不可见，未知页面一律当可见；
- **任何一次退栈都把栈顶救回可见**（`why = 'top'`），不依赖 `show` 一定派发；
- **取不到页面对象时退化为「不门控」**：组件照常工作，只是享受不到优化。

组件侧统一用 `bindPageVis(vm, fn)`：从 `vm.$root.$page` 解析所属页面（页面内子组件的 `$page` 不可靠，一律走 `$root`），立即回调一次当前真值，之后每次变化再回调，返回可调用的取消订阅函数。页面与页面内组件共用这一个入口。

两个封装（`bindPageVis`、`bindDl`）都**自己幂等**：页面会挂两遍（平台坑 6），第二次 `mounted` 执行 `this._visOff = bindPageVis(...)` 时只会覆盖字段，上一组订阅就成了没人释放的孤儿——每次可见性变化或 400 ms 下载广播都还在往 vm 里灌数据。因此绑定入口先调用同一 vm 上的上一组取消函数再建新的；幂等性放在封装里，不依赖每个调用点各写守卫（漏一个就泄漏一份）。

存储用**数组**而非 `WeakMap`：本工程运行在 QuickJS 上，此前全仓库没有用过 `WeakMap`/`Map`/`Set`（能力未经真机验证），`perf_selftest.mjs` 有一条断言禁止新引入这三个容器。页面对象随平台销毁，`unload` 时顺手摘掉条目即可。

## 三、签名判重：`utils/player/sig.js`

500 ms 快照里绝大部分字段与上一帧完全相同（只有 `positionMs` 在走）。所以「变了没有」按**界面显示精度**判断，而不是按原始值判断：

| 签名 | 覆盖的界面事实 |
|---|---|
| `viewSig` | 曲目（id/曲名/歌手/专辑/封面/时长）+ 控制态（播放/暂停/循环/倍速/已缓存）+ 状态文案 + 已播时间（`m:ss`）+ 总时长 + 进度百分比（0.1% 一档） |
| `queueViewSig` | 队列列表采样 + 当前曲 + 当前索引 + 循环模式 + 播放态 |
| `queueSig` | 队列长度 + 首尾各 8 个 id（队列可能上千首，逐首拼会退化成每 tick 一次 O(n) 字符串构造） |

判重不做深度比较、更不 `JSON.stringify`：快照里带整个队列与曲目对象，每 500 ms 序列化一次比渲染还贵。签名只拼界面真正消费的那几列，成本是几十个字符的加法。

判重口径的口诀是**签名必须覆盖页面渲染用到的一切**，否则界面会停在旧值。所以看到 `positionMs` 的页面，签名里就得带上它的显示值——`viewSig` 为此同时带时间文本与进度百分比。

`player.vue` / `queue.vue` 的统一落点：

```js
onTick(s) {
  if (!this._visible) return   // 页面被盖住：丢
  if (!this._feed(s)) return   // 显示值没变：丢
  this.st = s
}
```

## 四、各订阅点的门控方式

| 订阅点 | 门控 |
|---|---|
| [player.vue](../src/pages/player/player.vue) | `onTick` 判可见 + `viewSig` 判重；露出时补一次快照 |
| [queue.vue](../src/pages/queue/queue.vue) | `onTick` 判可见 + `queueViewSig` 判重；露出时补一次 |
| [index.vue](../src/pages/index/index.vue) | `onPlayer` 判可见 + 卡片签名判重；露出时补一次 |
| [NowLyric.vue](../src/components/NowLyric.vue) | `onPlayer` 判可见 + 自带 `sync` 判重；露出时补一次 |
| [NowProgress.vue](../src/components/NowProgress.vue) | `onPlayer` 判可见 + 0.2% 量化判重；露出时补一次 |
| [LyricBoard.vue](../src/components/player/LyricBoard.vue) | **时钟与 `player` 订阅都随可见性起停**（33 ms 时钟 = 每秒 30 次推进 + 逐字状态推送；500 ms 快照会写 `active` 并给每条逐字行推时钟）；订阅本身保留，用于露出时重锚 |
| [TimerPanel.vue](../src/components/player/TimerPanel.vue) | `sleepTimer` 订阅（1000 ms 倒计时）在回调入口判可见；露出时用 `state()` 补一次最新值 |
| 下载类（主页 / list / plinfo / album / downloads / dltracks / dlqueue） | 统一走 `utils/player/dlvis.js` 的 `bindDl(vm, fn)`：订阅 + 可见性门控 + 挂载首帧快照 |
| [player.vue](../src/pages/player/player.vue) 的 `sleepTimer` 回调 | 不门控：只写 `timerOn` 布尔（值不变时 Vue 的 setter 直接返回，不触发重渲染），且要驱动「定时结束」提示 |
| [sleeptimer.js](../src/utils/player/sleeptimer.js) | 不门控：跨页存活的单例，模块加载时注册一次、永不注销 |

`bindDl` 把「订阅、判可见、补首帧」收成一个调用，返回可调用的取消订阅函数；页面 `beforeDestroy` 里 `this._dlOff()` 即可，不再直接碰 `onDl`/`offDl`。

## 五、已知且刻意保留的开销

这些不是遗漏；改之前先看对应理由。

| 开销 | 位置 | 为什么不动 |
|---|---|---|
| 歌词滚动用 JS 补间逐帧写 `transform` | [LyricBoard.vue](../src/components/player/LyricBoard.vue) | 平台 CSS `transition` 在内联 style 上不插值、`transitionend` 不触发、无 `Element.animate`，只能用 `setTimeout(fn,16)` 自己补间。顺带把渲染窗口化到可视范围 ±`BUF_PX` |
| 进度条填充/手柄写 `width` / `left` | [ControlPanel.vue](../src/components/player/ControlPanel.vue)、[SeekPanel.vue](../src/components/player/SeekPanel.vue) | 改 `transform: scaleX()` 依赖 `transform-origin`，而平台的 `transform-origin` 行为未经真机验证（手柄还叠加了负 margin 居中）；且这些更新在可见性门控之后已不会在后台发生。要改先上探针页验证插值与原点 |
| 封面取色 fork `ffmpeg`+`od` | [coverColor.js](../src/utils/coverColor.js) | 每张封面只算一次、结果常驻内存缓存 |
| 下载每片 2 次 `process.exec` | [下载引擎.md](下载引擎.md) | 传输层约束（`fs` 无写接口，只能走 curl） |
| `log()` 同时 `console.warn` + HTTP POST | [log.js](../src/utils/log.js) | 默认发布形态 `LOG_SRV` 为空 → 发往 127.0.0.1 并静默失败；只有注入 `BPNCM_LOG_SRV` 的调试构建才有 I/O。**播放器事件回调里不要打日志**（20~25 次/秒） |
| `accentMixin` 每个实例各订阅主题事件 | [theme.js](../src/utils/theme.js) | 主题色变更只在设置页发生（低频），每实例一份监听远小于为它引入层级缓存（广播是单个 `$falcon` 事件，不分发也不重渲染）；`bindTheme` 已按实例去重，重复挂载不会留下第二份监听。若将来出现主题切换卡顿，先查这里 |
| 长列表按批渲染 50 行 | [list.vue](../src/pages/list/list.vue) | 平台单次渲染上限就是 ≤50 行（平台坑 5），这是最优分页策略 |

## 六、自检

无设备也能跑的两道检查：

```bash
node scripts/perf_selftest.mjs      # 纯逻辑约束测试（40 项）
python scripts/theme_verify.py      # 主题 / 模板绑定 / 混入契约 / 导航表
```

`perf_selftest.mjs` 守三件事，都是「改坏了看代码看不出来」的：

1. **签名语义**：同一快照必须判为「没变」；任何界面可见字段变化必须判为「变了」；进度按显示精度量化（0.1% 以内的差视作同一档）。
2. **可见性语义**：默认可见、`hide`/`show` 切换、重复同值不重复回调、`unload` 摘除条目、取消订阅后不再回调、取不到页面对象时 fail-open。
3. **静态扫描**：`player.on` / `onDl` / `sleepTimer.on` / `bindDl` / `bindPageVis` 的调用点必须在白名单内，且**条数要和白名单登记的一致**——只登记文件名的话，往已列入白名单的文件里再塞一条未门控的裸订阅不会有任何断言失败；扫描前先剥掉注释（注释里的用法示例不算调用）。播放页子面板的订阅回调入口必须判 `_visible`，每个订阅都必须被释放，且不得引入 `WeakMap`/`Map`/`Set`。

这些断言证明的是**语义与接线正确**，不是帧率提升——真机帧时间需要在设备上实测。在没有设备的环境里，这是能做到的上限，也是最该守住的部分：门控写错的表现是「页面不刷新」，这类 bug 在静态阅读时几乎看不出来。
