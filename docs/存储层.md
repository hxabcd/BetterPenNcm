# 存储层：数据落在哪、各走哪条通道

本文说明 BPN 的数据布局与写入通道。布局本身由 [`存储重构.md`](存储重构.md) §2 定义，
[`../src/utils/paths.js`](../src/utils/paths.js) 是路径的唯一真源 —— 本文不复述路径清单，
只讲「为什么这样分」与「写进去的代价是多少」，两者都是改存储相关代码前必须知道的约束。

## ⚠️ 两条硬规矩（改存储代码前先看这里）

1. **不要用 shell 写文件。** 平台 `fs` 没有写入接口，所以「写文本文件」只能
   `process.exec('/bin/sh', ['-c', 'printf ... > tmp && mv -f ...'])`，而一次 exec
   就是一次 fork —— S7 真机实测 **92~139ms/次**。内容超过 60KB 还要分片，每片再一次 fork。
   所有文本数据（配置 / Cookie / 播放快照 / 播放历史 / 每曲元数据 / 每曲歌词）都在
   **SQLite** 里，写是单行 upsert，微秒级、天然原子。
2. **数据库用原生 `sqlite3` 模块，不要用 `sqlite3` CLI。**
   `const m = await import('sqlite3'); new m.Database()` 在 S7 上可用（已验证
   open/exec/prepare/bind/step/run/columnNameList/finalize 全通，中文与引号逐字节无损）。
   CLI 那条路每次调用一次 fork，还得把 SQL 写进临时文件再 `.read`（因为 SQL 走命令行参数会
   被代码页转换，中文变乱码）。别再退回去。

同一份 **134KB** 数据在 S7 上的实测对照（2026-11-15，探针工程测）：

| 通道 | 写入 | 读回 |
|---|---|---|
| shell 分片写文本文件 | **2511 ms** | — |
| 原生 sqlite3（bind + step） | **10 ms** | 2 ms |

差 251 倍。这就是「切歌卡 5 秒」的直接来源 —— 一次快照要连续写两次。

## 一、两条通道

| 通道 | 实现 | 单次代价 | 用在 |
|---|---|---|---|
| **原生 `fs`** | 平台模块（`exists/stat/statfs/readdir/readFile/mkdir/rm`） | µs 级 | 所有目录/文件操作、轮询 |
| **原生 `sqlite3`** | 平台模块（`Database` / `Statement`） | µs 级 | **所有文本数据** |

平台 `fs` **没有写入接口**（`writeFile` / `appendFile` / `rename` / `unlink` 都是
`undefined`），但 `mkdir` 与 `rm` **是递归的**（`mkdir('a/b/c')` 一次建多级、
`rm('dir')` 连内容一起删）—— 所以建目录与删目录也不需要 shell。
`fs` 读接口面、exec 的 fork 成本与 `/bin/sh -c` 纪律见
[`docs/应用内系统访问能力_2026-10-10.md`](../../../docs/应用内系统访问能力_2026-10-10.md)。

## 二、为什么数据都在 SQLite 里

索引表（`album` / `artist` / `track` / `track_artist` / `playlist` / `playlist_track`）
进库的理由是「条目多、单条小、按 id 增删改」：单条 upsert 的代价与库规模无关，
而旧的「一张表一个 JSON 文件、整表读写」写任意一条都要重写整份。

文档类数据（`kv` / `track_meta` / `track_lyric`）进库的理由是**写频次与写入时机**：
播放位置快照每 15 秒一次、切歌/暂停/seek 还会即时触发，队列 500 首时快照约 134KB；
下载一首歌要写元数据两次、歌词一次，全在播放链路上。这些以前走 shell 分片写，
每次都是几百毫秒到两秒级的同步阻塞。

访问模型：索引表 **boot 整表灌内存 + 写穿**（`open()` 时一次导出到内存，此后查询
不再查库）；文档表按 key 直查，不预载。

## 三、data 目录只剩库 + 媒体目录

```
data/
  local_index.db   索引表 + kv 文档表 + 曲目元数据/歌词（唯一的数据库文件）
  cookie.txt       调试通道：从 PC 递一份会话进来（启动时导入一次，导入后进库）
  ncm_ck.txt       curl 登录用会话 jar（curl 自己写，我们只读）
  downloads/  cache/              每 track 一个目录（见 存储重构.md §2）
```

每个 track 目录里只有**音频与封面**（`track.mp3|flac`、`cover.jpg`）。
`metadata.json` / `lyrics.json` **不再存在** —— 它们在 `track_meta` / `track_lyric` 表里。

旧的 `storage/`（`preferences.json`）与 `store/`、`lrc/`、`covers/`、`music/` 目录
**不再创建**；升级时由 [`../src/utils/migrate.js`](../src/utils/migrate.js) 一次性搬过来，
旧目录保留不删（见 [`存储重构.md`](存储重构.md) §4）。

## 四、失败语义

**文件和库都是真相，没有第二份兜底**：

- 写失败只记日志，不抛。内存里的数据仍在，下一次写会重试（`fsutil` / `db` / `store` 都是这个约定）。
- 库可丢：`sqlite3` 原生模块不可用时降级为空库，上层按「没有本地索引」降级显示，
  索引能从文件与网络重建 —— 这比「整个应用起不来」好。
- 文件系统是唯一事实：任何「索引说有、文件却没有」的状态都不维护，列表一律以实际扫描为准。

## 五、什么时候需要再考虑换方案

- 出现「一次写必须在亚毫秒级完成、且不能碰文件系统」的新需求（当前没有：最高频的
  播放位置快照走的是单行 upsert，代价与内容大小无关）；
- 或索引规模涨到「整表灌内存」本身成为启动瓶颈（当前 `open()` 是一次导出 + 内存字典，
  实测规模为几百首量级）。

`fs.stat` / `fs.exists` 是原生调用、不 fork，轮询（如下载进度）只能用它 ——
这条约束见 [`下载引擎.md`](下载引擎.md) 的三条死线。

## 六、核对

```bash
D=/userdisk/secondary/miniapp/data/mini_app/pkg/8000200708310039/data
devctl run "ls $D; ls $D/downloads | head"
devctl run "sqlite3 $D/local_index.db .tables"
```

预期：顶层 `cookie.txt ncm_ck.txt local_index.db downloads/ cache/`；
`.tables` 列出 `album artist kv playlist playlist_track track track_artist track_lyric track_meta`。
