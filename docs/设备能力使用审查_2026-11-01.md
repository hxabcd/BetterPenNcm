# 设备能力使用审查（2026-11-01）

> ⚠ 时点快照：本文引用的 `src/utils/...` 行号与文件布局是审查时点的（2026-11-01 main）。
> 其后目录与分层重构（utils/ 退役 → core/ui/services 三轴）已整体迁移这些模块，
> 本文路径不再与当前仓库一一对应；结论与问题清单按内容读，路径按当时点理解。

## 1. 范围与结论

本次审查覆盖音频播放、下载/缓存、子进程与 shell、持久化、后台同步、输入法等设备能力调用。依据为当时源码和运行时文档；**未追加真机实验**，因此下文区分“代码可确认的问题”和“需要复核的边界”。

核心结论：当前最主要的问题不是使用 `curl`、shell 或 `stop()+偏移续播` 这些手段本身，而是若干实现把**设备事件、外部进程和磁盘状态当作天然可信、天然有序**，缺少会话隔离、总时限、持久化事务和冲突仲裁。由此产生的主要风险依次是：

1. 原生定时器与播放器包装层互相取消，可能误停新定时器或漏停播放。
2. 原生音频完成/同曲重放路径与应用状态机不完全等价，可能出现等待超时、进度陈旧和延迟自动下一首。
3. 下载被标为成功时不代表音频、索引和元数据已经完整、持久地落盘；故障恢复还存在静默“自愈”。
4. 外部进程只有数据空闲超时，没有覆盖排队、连接、阻塞读和退出的总时限，取消也不能保证终止底层进程。
5. 存储统计等同步 shell 调用可直接卡住 QuickJS 主线程。
6. 单曲下载、缓存共享和后台歌单同步各有索引或身份键缺口，长期运行后容易形成“文件在但入口没有”或“删了却下回来”。

未确认 P0 级问题。shell 拼接的远端输入安全性需要单独复核，本报告不把未验证的注入推测列为既定事实。

## 2. 高优先级问题

### P1-1：原生定时器回调没有“代次”，旧回调可取消新定时器

**证据**

- `src/services/player/sleeptimer.js:56-77` 给每首歌注册一个通用事件回调；旧回调不校验当前歌曲、当前定时器或当前任务代次。
- `src/services/player/sleeptimer.js:92-103,177-204` 播放过程中切歌时，旧任务可能仍未退出。
- `src/services/player/index.js:376-407` 的暂停、续播、seek 和切歌路径没有与原生定时器使用同一套取消协议。
- `src/services/player/index.js:1265-1287,1290-1348` 包装层的“取消计时”与原生层不同步。

**后果**

- 旧歌曲的 60 秒任务可以晚于新歌曲的任务触发，从而取消新任务。
- 两首歌在窗口边界连续结算时，旧任务可能清掉新任务刚保存的截止时间，导致播放结束后仍不暂停。
- 包装层显示“已计时”，原生层却可能仍直接暂停播放，行为依赖路径和时序。

**建议**

把定时播放收敛为一个所有者、一个活动任务和一个单调递增的会话号。回调执行前同时校验歌曲、会话号和定时器代次；任何暂停、seek、切歌、退出都走同一取消入口。不要让原生定时器与 JS 包装层分别维护互相不知情的“当前任务”。

### P1-2：原生播放完成路径绕过正常状态同步

**证据**

- `src/services/player/index.js:1251-1287` 的 `_nativeListen` 在首曲完成时不按正常完成路径回写 `elapsed`，仅移除监听并切索引。
- `play()` 的 Promise 只由 `play` 事件结算；同曲重新 `playFile` 若走原生完成监听路径，本次调用没有立即完成的事件，只能等待外层超时。
- 同一文件的“已暂停”状态主要依赖 `uuid`，但上层新会话仍可能晚一步读到旧的 `curUuid`。

**后果**

- 完成前的旧播放位置可能被下一段播放或 seek 复用。
- 同曲重放可能表现为无响应直至超时，而非立即开始。
- 延迟回调可能在新会话已经建立后继续推进队列，形成“晚到的自动下一首”。

**建议**

将“开始播放”和“自然结束”统一成应用层状态机事件：自然结束时先结算最终进度，再检查当前会话是否仍有效，最后推进队列；同曲立即完成的路径应直接结算对应 `play()` Promise。所有晚到事件必须携带并校验会话号，不能只依赖歌曲 id 或 uuid。

### P1-3：下载成功状态早于完整的持久化提交

**证据**

- `src/services/player/download/tasks.js:329-396` 先将任务标记为 `ok`，随后才登记曲库、歌单索引和歌曲元数据。
- `src/services/player/cache/files.js:12-38` 元数据采用直接覆盖写，没有临时文件、flush/fsync 和原子 rename。
- `src/services/player/download.js:59-86` 的启动恢复主要根据音频是否存在修正状态，不能完整恢复多步事务。
- `src/services/player/download/scheduler.js:112-146,148-170` 与 `src/services/player/cache/files.js:47-49` 存在“索引不在内存/元数据缺失就删除磁盘文件”的静默修复路径。

**后果**

设备掉电、进程退出或磁盘写失败时，可能出现任务显示成功但索引或元数据缺失；下一次启动又可能把实际可播放的文件当作孤儿删除。共享缓存时，归属表和元数据不一致还可能误删其他歌曲正在使用的 range。

**建议**

定义明确的下载提交协议：临时文件写入并校验 → 持久化元数据 → 原子改名 → 建立归属和索引 → 最后标记成功。启动恢复只重建或进入“待确认/待修复”，不能默认删除；引用计数和元数据更新必须属于同一事务或可重放日志。

### P1-4：外部下载进程没有总时限，取消也未形成闭环

**证据**

- `src/core/platform/exec.js:55-71` 的 `execAsync` 只封装进程退出和输出上限，没有绝对超时。
- `src/core/infra/net/fetcher.js:32-79` 在应用层等待进程退出，不能在底层阻塞时主动结束进程。
- `src/services/player/download/curl.js:42-75` 的超时主要保护连接和低速传输；即使应用侧 watchdog 触发，也不等于 curl 已退出。
- `src/services/player/download/curl.js:296-299` 表明已有“watchdog 触发但子进程仍存活”的已知场景。
- `src/services/player/download/tasks.js:288-326,417-420` 的取消操作没有完整接管底层进程生命周期。

**后果**

慢速持续传输、连接异常或不可中断的读操作可让任务长期占用队列；界面显示取消后，后台仍可能继续写文件或占用进程槽位。

**建议**

给每个下载任务设置覆盖排队、连接、传输、关闭的总 deadline；进程层提供真实取消句柄和退出确认。超时、取消、应用退出都必须停止写入并等待回收，之后才允许清理或复用目标文件。数据空闲 watchdog 只能作为附加保护，不能代替总时限。

### P1-5：后台歌单同步会把“删除”误当作“缺失”，并自动补回

**证据**

- `src/utils/local/lists.js:161-188` 的 diff 主要识别新增和已有项，没有表达用户删除的墓碑或版本信息。
- `src/utils/local/lists.js:361-376` 在拉取刷新后直接调用 `rebuildDownloads`。
- `src/services/ncm/playlists.js:48-90` 与 `src/pages/downloads.vue:128-151` 显示刷新会进入已下载歌单。
- `src/services/player/dlorigin.js:30-54` 允许重建下载归属，使“服务器还有”盖过“本地已删”。

**后果**

用户在本机删除歌曲后，后台刷新可能重新建立归属并再次下载；若用户首次手动删除前还没有快照，全部删除更容易被解释成需要重建。该行为也带来非预期流量和存储占用。

**建议**

区分“尚未同步”“远端新增”“用户本地删除”“远端撤销”。本地删除必须留下可同步的墓碑或版本状态；自动后台同步只处理明确的远端新增，不得静默逆转本地删除。需要修复归属时向用户显示差异并请求确认。

## 3. 中优先级问题

### P2-1：单曲下载没有进入可见的统一索引

`src/utils/local/lists.js:53-59` 的单曲列表只从歌单归属推导，`src/services/player/locallists.js:121-138` 会过滤没有歌单归属的 id；`src/services/player/download/tasks.js:367-368` 对普通任务默认 `plIds=[]`。结果是单曲文件和曲库记录可能存在，但下载管理页没有对应入口，只能依赖其他搜索或历史路径发现。

建议增加独立的“单曲下载”归属类型，而不是借用歌单关系表达所有本地下载。

### P2-2：共享缓存的身份键不足以证明内容相同

`src/services/player/cache.js:28-68` 用 range 和缓存块复用不同 URL 的内容；`src/services/player/cache/files.js:27-31` 只持久化完整音频的一个 URL，`src/services/player/download/source.js:42-112` 的换源和分片元数据没有共同校验完整来源身份。

同一歌曲的换源共享可以保留，但至少应把来源类型、音质、必要请求头、最终有效 URL/内容校验和纳入身份。分片续传还应校验 `Content-Range`、ETag/Last-Modified（若可用）和总长度，不能只凭“文件存在且非空”复用。

### P2-3：同步 shell 调用阻塞 UI 主线程

`src/core/platform/exec.js:33-36` 的 `execSync` 没有同步超时；`src/services/player/storagestats.js:24-49` 用同步 `du/find` 扫目录，`src/pages/settings.vue:121` 和 `src/pages/setdl.vue:35` 又会在页面挂载时触发统计。大目录或存储异常时，整个 UI 会等待 shell 返回。

建议统计异步化、串行化并缓存结果；页面先显示旧值或“统计中”，后台完成后再刷新。所有可能访问大目录或外部介质的同步调用都应移出交互路径。

### P2-4：持久化写入普遍缺少崩溃一致性

`src/utils/storage/util.js:26-52,73-90`、`src/utils/storage/prefs.js:32-38` 和下载元数据写入均采用直接覆盖。字符串 KV 和临时文件由平台限制可以理解，但“直接覆盖唯一副本”不是唯一选择。

建议至少采用“临时文件完整写入 → 校验 → 原子替换”，重要文件保留上一版；解析失败时报告并恢复备份，而不是立即把坏状态扩散到索引和缓存清理逻辑。

### P2-5：请求队列缺乏取消，旧请求可能覆盖新歌曲状态

`src/services/player/requestqueue.js:34-52` 主要按歌曲合并请求，没有在切歌后取消旧歌曲的完整请求链；`src/services/player/download/source.js:57-64` 也会继续为旧请求解析来源。若此时存在同曲旧缓存，旧任务可能被后续状态误认为当前内容。

建议队列项绑定播放会话和取消信号；只有当前会话允许更新播放状态，其他请求即使完成也只能写独立缓存，不得推进 UI 或播放器。

### P2-6：进度事件合并会丢掉最终状态

`src/services/player/downloads/progress.js:87-92` 按歌曲只保留一个 pending，重复下载或分片交错时可能以旧进度覆盖新进度；`235-270` 没有“同代次只保留最新”的严格规则。通常只是短暂显示回退，但也可能留下错误的列表进度。

建议按任务代次和序号合并，始终保留最新事件；最终完成事件不可被普通进度覆盖。

### P2-7：系统输入法桥接是设备全局副作用，缺少页面生命周期兜底

`src/utils/textedit/bridge.js:71-98,174-183` 通过全局对象与系统输入法协作。该方案符合平台限制，但若页面异常退出或组件未正常销毁，桥接对象和回调可能残留。

建议将桥接生命周期绑定到页面/组件会话，退出时强制解除；回调携带会话号，拒绝上一页面晚到的文本事件。

## 4. 需要复核，但不作为已确认高危结论

### shell 参数与远端输入

`src/core/infra/net/fetcher.js`、`src/services/player/download/curl.js`、`src/services/player/download/curl/tail.js` 大量通过 `/bin/sh -c` 组织 curl 和文本处理。必须逐条复核 `shellQuote`、路径白名单和 URL 协议校验： shell 引号可防普通 shell 元字符，但不能阻止前导 `-` 被 curl 当成选项；如果引号实现不完整，含单引号的远端字段也可能改变命令结构。

在复核完成前，不把它定性为“远端命令执行已成立”。整改方向是优先使用参数数组，避免 shell；必须使用 curl 时固定 `--`、协议白名单和输出路径，并检查最终有效 URL 与响应类型。

### 日志识别传输结束

现有实现需要 tail/正则补偿设备日志格式和缺失回调，这属于可理解的适配。但它不应成为唯一完成信号：必须同时以 curl 退出码、文件长度和响应元数据确认成功，并保证 watchdog 后能回收进程。

## 5. 平台原语与适配边界

**需要保留的是平台能力语义，不是当前 workaround 的原样实现。** 底层可以迁就平台，但业务层不应被迫理解这些差异；平台适配应集中在最底层，并提供正常、完整的领域接口。

| 平台能力 | 可接受的底层适配 | 不应向上泄漏的细节 |
|---|---|---|
| 暂停/续播 | 无 pause 时可在适配器内用 `stop()` + 偏移 `playFile` | 上层不应自行 stop、保存偏移或判断原生暂停状态 |
| 媒体事件 | 适配器内按 uuid 过滤全局广播 | 业务层不应处理 uuid、同曲重放和晚到原生事件 |
| 大文件传输 | 内建 http、原生扩展或受监督的 curl 后端 | 任务层不应关心 curl 参数、日志格式和进程回收方式 |
| 设备输出识别 | tail/正则只能作为兼容后端的内部细节 | 不能用日志猜测代替进程退出和文件完整性判断 |
| 目录统计 | 可以使用 `du/find` | 页面不应同步等待 shell；统计需异步、限时和缓存 |
| 字符串 KV | 适配器内完成序列化和反序列化 | 调用者不应处理字符串格式、覆盖写和损坏恢复 |
| 有效播放计时 | 60 秒阈值可作为明确业务规则 | 定时策略不应与原生播放控制分别维护状态 |
| 系统输入法 | `Global.startTextEdit` + JS 桥接可放在适配器内 | 页面不应直接管理全局桥接对象；回调必须按会话隔离 |

## 6. 建议整改顺序

1. **先修播放时序**：统一原生/包装定时器和播放会话，消除旧回调影响新会话。
2. **再修下载事务**：把成功状态放到最后，元数据和索引可恢复，禁止无提示删除“孤儿”文件。
3. **补齐进程生命周期**：总 deadline、取消、kill/退出确认和清理必须由同一任务所有者负责。
4. **建立下载身份模型**：区分歌曲 id、音源、音质、URL、缓存内容和本地归属；单曲下载单独建索引。
5. **移除主线程阻塞**：存储统计、目录扫描和日志采集全部异步化。
6. **最后处理体验与健壮性**：请求取消、进度合并、输入法桥接清理、持久化备份。

## 7. 验收重点

- 连续切歌、暂停、seek、同曲重放和自然结束时，旧回调不能改变新会话。
- 在下载各阶段强制退出应用/设备后，重启只能得到“完整可用”或“明确待恢复”，不能显示假成功或静默删文件。
- curl 假性存活、低速持续传输、无响应连接都能在总时限内取消并回收。
- 本地删除后刷新歌单不会自动补回；单曲下载始终有管理入口。
- 大目录统计期间 UI 仍可交互；异常存储不会产生永久同步等待。

## 8. 更优雅的实现方向

### 8.1 分层原则

目标不是增加目录和接口数量，而是让每个平台差异只有一个负责人：

```text
业务意图
  → 会话与状态机（唯一事实源）
    → 能力适配器
      → SoundPlayer / http / curl / fs 等平台原语
```

业务层只表达播放、暂停、定位、下载等意图；会话号、操作代次和持久化事务由领域层维护；平台 workaround 只允许存在于适配器内部。除传输后端等确有多实现需求的位置外，不增加通用插件式抽象。

### 8.2 音频：会话状态机代替补丁式调用

业务层只接触正常播放语义：

```js
audio.load(track, { position, rate })
audio.play()
audio.pause()
audio.seek(position)
audio.stop()
```

`pause()` 内部是否使用 `stop()` 与偏移恢复，由 `AudioEngine` 自行决定。关键约束是：

- `load/play/pause/seek` 进入同一个命令队列，页面和其他模块不得直接操作 `SoundPlayer`。
- 每次切歌生成 `sessionId`，每次操作生成 `opId`；旧歌曲、旧请求和旧定时器的晚到事件直接丢弃。
- `play()` 只在状态机确认进入播放后结算；同曲立即完成也走同一结算路径。
- 定时播放只订阅该状态机，不单独操作原生播放器。原生 `playAtMostSec` 如仍需要，只能作为 `AudioEngine` 内部的执行细节。

这样即使最底层仍使用 `stop+偏移续播`，它也不会再扩散为业务层的特殊分支。

### 8.3 下载：分离传输、任务和内容库

#### Transfer：只负责取得字节

```js
const job = transfer.start({ url, headers, destination })
job.onProgress(...)
await job.done
// 或 job.cancel()
```

后端按能力选择：先验证内建 `http.download` 是否满足需求；下载作为核心功能时，可用小型原生扩展统一处理请求、临时文件、进度、取消和结果校验；curl 只保留为兼容后端。`tail+正则` 不应再是正常成功路径的必要条件。

#### DownloadJob：负责状态与恢复

```text
resolving → transferring → verifying → committing → ready
```

每次状态迁移均可持久化、可恢复；只有提交完成后才能显示成功。取消和异常必须等待底层传输真正退出，再允许清理或复用文件。

#### ContentStore：负责内容与引用

- 歌曲、音质和格式决定内容身份；签名 URL 只是临时定位符。
- 进行中的分片不跨歌曲共享，只有校验完成的完整文件才允许去重。
- 单曲、歌单和专辑都是内容引用，不再由某个归属表单独决定文件是否应该存在。
- 以简单可靠的所有权换取少量可放弃的空间复用，避免当前的交叉归属和静默修复。

### 8.4 其他能力的收口方式

- `ProcessRunner`：默认参数数组和异步执行，统一总超时、输出上限、真实取消、退出确认与资源回收；业务代码不再自行拼 `/bin/sh -c`。
- `JsonStore`：统一序列化、schema 版本、临时文件、原子替换和备份，调用者只读写结构化对象。
- `TextEditSession`：绑定页面生命周期，页面销毁即失效，上一页面的晚到回调不能写入新页面。
- 存储统计和目录扫描移出 QuickJS 同步路径，页面只订阅异步统计结果。

实施顺序沿用第 6 节：先以纯 JS 收口音频状态机，再定义传输接口并选择后端，随后重建下载任务与内容库，最后收口进程、存储和输入法。目标是边界闭合，而不是增加分层数量。

## 9. 现有代码的分层程度

### 9.1 已经具备的基础

当前代码并非没有架构，已有分层主要体现在：

| 方面 | 当前实现 | 评价 |
|---|---|---|
| 页面与业务组织 | `pages/`、`components/`、`services/player/`、`services/ncm/` 分工明确 | 基础结构清楚 |
| 下载模块组织 | `download.js` 门面，内部拆为 source、files、progress、scheduler、tasks、fetcher | 有明确模块边界 |
| 平台调用入口 | `exec.js`、`fsutil.js`、`paths.js` 和网络请求入口 | 避免了完全散落式调用 |
| 播放器集中管理 | 播放单例维护队列、进度和播放状态 | 已具备领域服务雏形 |
| 存储封装 | storage、prefs、filestore 等模块 | 调用方式基本统一 |

### 9.2 分层尚未闭合的地方

1. **模块分开了，控制权没有收拢。** `player/index.js` 与 `sleeptimer.js` 都能影响播放，原生和 JS 包装层又分别维护计时状态，没有一个模块能独立回答当前播放会话、有效操作和有效定时器。
2. **API 被封住，平台语义仍向上泄漏。** 上层仍需理解 uuid、stop 式暂停、同曲重放事件和两类定时器；现有封装解决了“不直接 import 原生 API”，尚未解决“不理解原生怪癖也能正确使用”。
3. **下载按流程拆分，却没有事务边界。** source、tasks、files、scheduler 各自负责一步，但文件完成、元数据、曲库、归属和成功状态之间没有唯一提交者，崩溃恢复也缺少统一协调。
4. **进程抽象没有覆盖生命周期。** `execAsync` 统一了启动和取结果，但总超时、取消、退出确认和回收仍由上层各自处理，下载层因此仍需理解进程和 curl 细节。

### 9.3 程度判断

以下是用于判断改造方式的相对评价，不是量化测试结果：

- **代码组织分层：7/10**。目录和模块职责已有较好基础。
- **能力边界分层：4/10**。部分平台差异仍穿透到业务层。
- **状态与一致性分层：3/10**。音频和下载均存在多个局部事实源。

因此不需要推倒重来。应保留现有页面结构、下载门面和平台工具入口，重新分配状态所有权：在播放器内形成闭环音频状态机；让下载提交、内容文件和引用关系各有唯一负责人；把 `exec.js` 从命令封装补全为进程生命周期接口。概括来说，当前已有“分层的外形”，下一步需要补的是“分层的约束力”。
